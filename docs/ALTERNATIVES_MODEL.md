# Альтернативы по стоимости и обслуживанию

Этот расчёт использует тот же многопериодный MILP, что основной план. Все инвестиционные решения общие для сценариев неопределённости; только эксплуатация может различаться. География, кандидаты, времена поездки, ограничения сети, батареи, PV, годовые бюджеты и CVaR берутся из неизменяемого `PlanningInput`.

Для каждого целевого уровня `f` решается задача:

```text
минимизировать  Σ_y CAPEX_y
при условиях   served(y, q) ≥ f × demand(y, q)  для каждого года y и сценария q
               + все исходные физические, бюджетные и рисковые ограничения
```

Если спрос в отдельном году и сценарии равен нулю, это ограничение пропускается. Если недостижимые зоны делают требование невозможным уже по верхней оценке спроса, ответ `infeasible` возвращается с годом и сценарием. Иначе статус берётся от HiGHS. После доказанного минимума CAPEX дополнительная лексикографическая стадия максимизирует обслуженную энергию при стоимости не выше минимума плюс 0,01 ₽, затем выбирает лучшую сценарную экономику при сохранении обслуживания. Это убирает произвольное недоиспользование уже построенной инфраструктуры. При лимите времени и допустимом incumbent возвращается `feasible`, а не ложный оптимум.

Go worker сейчас запрашивает уровни `0`, `0.5` и `1`, выделяя не более 20 секунд решателя на каждый. Python API допускает до пяти уникальных отсортированных уровней; пустой список выключает альтернативы. Основной план и каждая допустимая альтернатива проверяются одинаковыми seed событийной симуляции. Для одинаковых инвестиционных решений детерминированный результат симуляции переиспользуется в пределах одного запроса. Ответ содержит `service_by_year` для каждой пары год × сценарий и фактически достигнутый минимальный уровень обслуживания. `same_investment_as_target` указывает только совпадение инвестиционных решений, а не тождество всех результатов оптимизации.

Статус `optimal` доказывает минимум CAPEX только на переданном наборе кандидатов, дискретизации и входных сценариях. Эта конечная сетка целевых уровней не доказывает полный фронт Парето по CAPEX, доступности, NPV и риску. Симуляция очередей пока не диспетчеризует накопитель и PV; её результат не следует трактовать как подтверждение энергетического режима. Данные с меткой `assumed` остаются предположениями независимо от математического статуса.

Проверки включают полный перебор четырёх масок строительства в задаче из двух площадок, несовместимый бюджет, недостижимый спрос, запрет компенсации дефицита первого года вторым, нерентабельный для оператора обязательный план, проверку схемы API и сквозной запуск через PostgreSQL и worker.
