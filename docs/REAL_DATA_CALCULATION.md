# Что в расчёте является наблюдением, а что моделью

Система решает MILP по переданным площадкам и проверяет план независимой минутной событийной симуляцией. **Корректное вычисление на реальных входах не делает автоматически реальными отсутствующие входы.** Для решения о строительстве нужны подтверждённые площадки, стоимость оборудования, условия подключения, дорожная матрица, тарифы и оценка как обслуженного, так и скрытого неудовлетворённого спроса. Встроенный сценарий синтетический.

Помимо CSV выполненных сессий доступен [предварительный расчёт потенциального спроса из маршрутов и стоянок](MOBILITY_DEMAND.md). Он создаёт заявки там, где зарядки пока может не быть, и проверяет батарею, окно зарядки и баланс энергии. Это **сценарная проекция из предоставленных поездок**, а не выявление всех скрытых поездок города или прогноз, прошедший проверку на истории. Для инвестиционного вывода её нужно калибровать независимыми транспортными данными и проверять на отложенном периоде.

## Зарядные сессии: точный смысл CSV

Команда из [пошагового запуска](../START_HERE.md) принимает `session_id,zone_id,started_at,ended_at,energy_kwh`. ID уникальны; даты содержат UTC-смещение и полностью входят в объявленное окно наблюдений; энергия положительна. Зона без сессий отклоняется. Входные байты хешируются SHA-256 и записываются вместе с источником и выбранным `kind`.

Из каждой зоны выводятся:

| Поле | Расчёт | Что означает |
|---|---|---|
| `hourly_kwh[24]` | Энергия сессии распределяется **равномерно по её длительности**, затем суммируется по местным часам и делится на число календарных дней | Оценка профиля **уже отпущенной** энергии, не измеренная интервальная мощность |
| `mean_session_kwh` | Сумма `energy_kwh` / количество сессий | Фактический средний объём выполненной сессии из этого CSV; старое сценарное значение заменяется |
| `arrival_profile.hourly_sessions[24]` | Количество **начавшихся** сессий в местном часе / число дней | Отдельный профиль прибытий, не смешанный с почасовой нагрузкой |
| `hourly_count_variance[24]` | Выборочная дисперсия суточного количества стартов по каждому часу | Наблюдаемая нестабильность по дням; при короткой истории не используется для подгонки сложного распределения |
| `energy_quantiles_kwh[101]` | Эмпирические квантили объёма сессии 0–100% | Распределение отпущенной энергии, из которого симулятор генерирует объём новых заявок |

Проверяется инвариант `sum(hourly_kwh) = mean_session_kwh × sum(hourly_sessions)` для типичных суток. `sample_count` и `observation_days` доступны в контракте. `source_kind = observed` — **заявление поставщика**, не независимая проверка CSV; `hourly_load_method = uniform_session_duration` явно фиксирует способ восстановления нагрузки. Если доступны интервальные показания счётчика, их нельзя подменять равномерной аппроксимацией: для них нужен отдельный адаптер и `hourly_load_method = measured_interval`.

Суточный знаменатель требует подтверждённого покрытия выгрузки. Если в окне наблюдения по зоне нет сессий, импорт откажет: неизвестно, был ли это настоящий ноль или отсутствующий файл/счётчик. `coverage_complete=true` в API (`--coverage-complete` в CLI) разрешает такие дни только по явному заявлению поставщика, что экспорт охватывает **каждую зону и дату**, включая дни с нулём. В профиле сохраняются `days_with_sessions` и `coverage_complete`; `metadata.input_quality` различает неподтверждённое покрытие и заявленное полное покрытие. Это не удостоверение достоверности выгрузки.

## Как эти данные используются

Для **CSV выполненных сессий** MILP использует полученный `hourly_kwh` как сценарный объём энергии в почасовых интервалах и ограничивает оборудование, подключение, общий узел, PV, накопитель и бюджет. Это приближение, особенно для сессий, переходящих между часами. Для отдельного пути потенциальной потребности из маршрутов датированные `charging_requests[]` распределяются по фактическим окнам; формат — в [DATED_DEMAND.md](DATED_DEMAND.md). `optimal` относится только к переданным кандидатам, профилям и ограничениям.

Для **CSV/типового профиля** SimPy генерирует автомобили по `arrival_profile.hourly_sessions`, если профиль есть. При достаточной истории (не менее 7 дней и 30 сессий) и дисперсии выше среднего количество стартов в час моделируется отрицательным биномиальным распределением; иначе — распределением Пуассона. Объём сессии берётся из эмпирических квантилей. Без профиля число стартов выводится из `hourly_kwh / mean_session_kwh`, а объём генерируется положительным гамма-распределением с заданным коэффициентом вариации 15% — это **допущение**, не наблюдение. Для датированных заявок времена и энергия приходят из входа, а дробные веса и множители роста дают seed-зависимое округление числа машин. В обоих режимах результат содержит seed. Независимые часы и повтор типовых суток относятся к старому профильному режиму; короткий календарь заявок не является годовой сезонной историей.

Минутный диспетчер соблюдает мощность постов, подключения и общего узла, КПД и SoC накопителя. Сеть заряжает накопитель только если известный типовой профиль показывает будущий час, в котором прямой мощности сети и PV недостаточно; иначе бессмысленная ночная покупка не включается в расходы симуляции. Это причинная политика по **прогнозному профилю**, не знание будущих случайных прибытий. При ошибке профиля она может недозарядить накопитель; такой дефицит должен отразиться в эксплуатационном разрыве.

В `simulation[]` отдельно даны `arrivals_by_hour`, `requested_energy_kwh`, `energy_kwh`, `unserved_energy_kwh`, очереди и энергетический аудит. `operational_validation[]` сравнивает **долю** обслуживания MILP со средним и диапазоном долей SimPy для одной пары год × сценарий. Если события, очереди или ограничение мощности уменьшают долю, `service_gap_percentage_points` положителен. По умолчанию этот разрыв диагностический; opt-in `run-spec-v2` допускает до трёх попыток улучшения на отдельных seed разработки и затем проверяет выбранный вариант на финальных seed. Это ограниченная эвристика, не гарантированное устранение разрыва. Три seed по умолчанию доказывают воспроизводимость запуска, но не дают статистически устойчивой оценки: для сравнительного эксперимента задавайте не менее 30 одинаковых финальных seed для всех планов.

В профильном режиме `parameters.simulation_days` задаёт непрерывные 1–14 суток (по умолчанию 3); датированный режим использует 1–14 объявленных локальных `covered_dates`, включая 23/25-часовые дни. Минутный диспетчер не обнуляет SoC, сессии или очереди в полночь. `arrivals_by_day_hour` и `day_dispatch` показывают отдельные сутки, включая SoC и ожидающие сессии на границе; агрегаты `simulation[]` охватывают **весь горизонт**. Для календаря короткого горизонта годовая экстраполяция использует явно заданный `annualization_factor` с основанием `assumed_repeat`; для старого профиля действует прежняя нормировка на сутки и множитель 365. Профильные зоны повторяют одни типовые сутки; у датированных зон реальные рабочие/выходные представлены только настолько, насколько они различаются во входных заявках.

`operational_economics[]` для каждого сценария повторно считает NPV по **отпущенной в SimPy энергии**, фактическому сетевому потреблению, разряду накопителя, фиксированным затратам и инвестициям по годам. Он возвращает среднее/минимум/максимум по seed, разницу с NPV MILP и флаг смены знака прибыльности. Используются те же заданные цены и коэффициент дисконтирования; экстраполяция по 365 или `annualization_factor` остаётся **предположением о повторяемости короткого периода**. Это более строгая внутренняя проверка рекомендации оператора, **не** измеренный годовой денежный поток и не рыночный прогноз.

`metadata.input_quality` указывает зоны с наблюдённым, предположенным и параметрическим профилем, короткую историю и ограничения интерпретации. Даже реальные выполненные сессии **не показывают** людей, не приехавших из-за очереди, недоступной станции или отсутствия зарядки. Поэтому `unmet_kwh` — дефицит **переданного модельного спроса**, не измерение всего неудовлетворённого спроса города. Для оценки скрытого спроса нужны дополнительные транспортные данные и проверка на отложенной истории.

## Минимальный воспроизводимый контур с данными оператора

1. Подготовить исходный `PlanningInput` с идентификаторами зон и явно помеченными площадками, дорогами, узлами и экономическими параметрами. Не заполнять неизвестный резерв сети нулём или выдуманным «реальным» значением.
2. Получить выгрузку сессий с разрешением на использование и интервалом наблюдений; загрузить её через `POST /api/v1/scenarios/{id}/imports/sessions` с `kind=observed` **только** для действительно наблюдённой выгрузки. API создаёт новую версию данных и новый сценарий, сохраняет точные байты CSV и SHA-256; формат и пример команд — в [руководстве](DIRECT_UPLOAD.md). CLI `python -m energy.ingest_sessions` использует тот же предметный адаптер для офлайн-подготовки.
3. Отдельно добавить дорожные времена из зафиксированного графа OSRM и подтверждённый почасовой резерв подключения через `POST /api/v1/scenarios/{id}/imports/grid-headroom`. Для узла без подтверждения сохранить `assumed`, а не менять метку ради внешнего вида отчёта. Каждая загрузка применяется к ID последнего нужного сценария, исходный снимок не перезаписывается.
4. Рассчитать план и проверить `optimization.verification.passed`, `simulation[].dispatch_verification.passed`, разрывы `operational_validation[]` и `operational_economics[]`, предупреждения `metadata.input_quality`. При значимом разрыве решение требует уточнения данных или модели до инвестиционного применения.

Проверки в репозитории доказывают сохранение энергии и числа сессий, разделение часа начала и часа нагрузки, использование эмпирических размеров сессий, физические пределы диспетчеризации и расчёт разрыва. Они **не** подтверждают достоверность стороннего CSV или техусловий присоединения.
