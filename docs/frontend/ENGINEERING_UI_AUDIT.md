## Пользователь и задача

Основной пользователь — инженер или аналитик оператора/города. Он выбирает входные данные и ограничения, проверяет несколько инвестиционных вариантов и обосновывает решение. Знание JSON, имён DTO и UUID не должно быть условием выполнения основной задачи.

Рабочая последовательность: данные → проверка полноты → условия сценария → запуск → анализ допустимости и сервиса → сравнение → отчёт. Ошибки должны вести к конкретному входному объекту или параметру.

## Каким должен стать интерфейс

### Компоновка

```text
Проект / территория     Сценарий · версия     Данные: есть допущения
─────────────────────────────────────────────────────────────────
Разделы         Основная рабочая область         Свойства объекта
Данные          Карта / таблица / график         Оборудование
Сценарии        Локальные фильтры                Подключение
Территория      Контекстные действия             Ограничения
Расчёты                                         Источник
Сравнение                                       Объяснение
Отчёт
─────────────────────────────────────────────────────────────────
Статус задачи · допустимость модели · выполнение требований
```

Правая панель появляется при выборе объекта. Страница импорта использует доступную ширину под форму и предпросмотр; ей не требуется постоянная карта или панель бюджета. На узком экране инспектор открывается поверх основной области. Состав разделов должен отражать доступные возможности: пока нет серверной сущности проекта, нельзя изображать фиктивное управление проектами.

### Варианты организации

1. Карта в центре всего приложения: удобно для территории, хуже для импорта и расписаний.
2. Пошаговый мастер: удобен при первом запуске, замедляет повторную работу эксперта.
3. Рабочее пространство с разделами, связанными представлениями и инспектором: подходит для повторных расчётов и сравнения.

Рекомендуется третий вариант. Мастер использовать для импорта и создания первого сценария; карту — как полноценное представление территории внутри рабочего пространства.

### Страницы и основные действия

| Экран | Основное содержание | Основное действие |
|---|---|---|
| Данные | Наборы, версии, дата покрытия, происхождение, ошибки и полнота | Добавить или обновить набор |
| Импорт | Файл → сопоставление полей → предпросмотр → ошибки → сохранение | Сохранить проверенную версию |
| Сценарий | Цель, годы, годовые бюджеты, тарифы, ограничения, требования сервиса | Сохранить и запустить |
| Территория | Карта и синхронная таблица площадок/узлов/зон | Проверить или изменить выбранный объект |
| Расчёт | Входная версия, этап выполнения, события, отмена | Открыть результат |
| Результат | Сводка, инфраструктура, эксплуатация, энергетика, экономика | Перейти к сравнению вариантов |
| Сравнение | Общая база сравнения, CAPEX, сервис, риск, статусы, различия объектов | Выбрать вариант для отчёта |
| Парк | Таблица машин и рейсов, зарядные окна, временная диаграмма SoC | Проверить выполнимость расписания |
| Коридор | Линейная схема маршрута, станции, достижимость, отказы | Проверить маршрут |
| Отчёт | Выбранный план, ограничения, источники, версии и протокол | Экспортировать доступный формат |

История расчётов, новые операции редактирования и экспорт требуют сверки с фактическими API; недоступные функции не заменяются демонстрационными ответами.

### Визуальная система

- Светлые рабочие поверхности, чёрный текст, нейтральные серые разделители. Тёмная шапка допустима, но должна быть компактной.
- Цвет — только семантический: предупреждение, нарушение, выбранный объект и различение графических рядов. Всегда добавлять текст, форму или штриховку.
- Основной текст ориентировочно 14–16 px, таблицы и подписи 13–14 px. Не делать системные предупреждения мелкими сносками.
- Заголовок страницы 24–28 px; крупные презентационные заголовки не повторяются над каждым инструментом.
- Числа выравниваются вправо, имеют разделители разрядов и единицы в заголовке. Доли отображаются в процентах, когда это предметно уместно.
- Слайдер бюджета дополняется точным числовым вводом; годовые бюджеты представлены таблицей.
- JSON доступен для специалистов в экспертном режиме. Основные рабочие операции выполняются через формы и таблицы.
- Плотность регулируется содержанием: компактные таблицы для сравнения, свободное место вокруг важных выводов.

## Состояния и доступность

Нужны: пустой проект/набор, загрузка, невалидный файл, частичная полнота, несохранённые изменения, очередь, выполнение, отмена, ошибка, несовместимые ограничения, непройденная приёмка, недостаточная проверка, успешный расчёт с допущениями.

Каждое состояние сообщает причину и доступный следующий шаг. «Расчёт завершён», «ограничения соблюдены» и «требования сервиса выполнены» остаются разными признаками. Технический код причины раскрывается по запросу.

При реализации проверить Tab/Shift+Tab/Enter/Escape, видимый фокус, связь ошибки с полем, объявления асинхронных статусов, контраст, масштаб 200%, работу таблиц с клавиатуры и отсутствие потери данных при смене раздела. Текущий CSS содержит `:focus-visible`; это не заменяет сквозной проверки.

## Предварительная экспертная оценка

Оценки субъективные, основаны на просмотренных экранах, а не на исследовании с пользователями.

| Направление | Оценка | Основание |
|---|---|---|
| UX инженерной работы | 4/10 | Конкурирующие действия, JSON в основном пути, слабая связь контекста |
| Визуальная система | 6/10 | Согласованная палитра, но неудачная плотность и подтверждённое переполнение |
| Путь до полезного результата | 5/10 | Демо выполняется; подготовка собственных данных требует знания контрактов |
| Доступность | Не оценена полностью | Есть семантические элементы и фокус в CSS; полная проверка не выполнена |

Решение аудита: требуется переработка структуры. Изменения интерфейса в рамках этого аудита не выполнялись.

## Порядок переработки и приёмка

1. Исправить overflow и несогласованное отображение выбранного сценария.
2. Создать компактную общую оболочку; убрать нерелевантную панель запуска со страниц импорта и отдельных моделей.
3. Выстроить подготовку входа через каталог, мастер импорта и предметный редактор.
4. Разделить результат по задачам анализа; вынести статусы и сравнение на первый уровень.
5. Добавить связанные таблицы/карту/инспектор; календарь, расписания и графики реализовывать по фактическим данным API.
6. Проверить полный пользовательский путь и доступность на 1440 × 900, 1280 × 800, 1024 × 768 и узком экране. Эти размеры — будущая матрица проверки, не выполненные тесты этого аудита.

Критерии: основной сценарий не требует JSON; бюджет и источник однозначны; любая метрика имеет период и происхождение; широкая таблица не расширяет весь документ; ошибки ведут к исправлению; сравнение использует явно указанную общую базу; результат доступен повторно по сохранённой версии.
