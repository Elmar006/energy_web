# Контракт бэкенда для фронтенда

Актуально для ветки `backend/algo`. Машинный контракт — [`openapi.json`](../../openapi.json); этот документ описывает пользовательские состояния и границы уже работающих вычислений. При изменении API обновлять оба файла в том же PR. Фронтенд здесь не меняется: это ТЗ на его следующую интеграцию.

## Данные и доверие

- Встроенный пример — **синтетический**. Координаты и реальные дороги OSRM не делают спрос или резерв электросети наблюдаемыми.
- Поле `provenance.kind` у зоны, площадки и узла: `observed` (заявлено как наблюдение), `derived` (вычислено из источника), `assumed` (сценарное допущение). Показывать `source`; `observed` сейчас не означает независимую проверку платформой.
- `datasets[]` фиксирует источник, SHA‑256, роль, вид данных и при наличии лицензию. Пустое значение нельзя рисовать как ноль.
- Величины: энергия — кВт·ч, мощность — кВт, деньги — ₽, расстояние — км, время маршрута — минуты. `investment_rub_by_year` — CAPEX по календарному году; `cashflow_rub` — сценарная дисконтированная экономика представительных суток, а не заключение о фактической окупаемости.
- `optimal` относится **только к переданным площадкам, сценариям и временной сетке**. Отсутствует AC power-flow и подтверждение техусловий присоединения; интерфейс не должен маркировать план «сетевой экспертизой».
- `scenario.spec.zones[].arrival_profile` появляется после импорта CSV сессий или в подготовленном наборе зон: `hourly_sessions[24]` — среднее число **начатых** сессий в локальный час за сутки, `hourly_count_variance[24]` — выборочная дисперсия суточного числа, `energy_quantiles_kwh[101]` — квантили 0–100%, `sample_count`, `observation_days`, `source_kind`, `hourly_load_method`, `provenance`. При отсутствии профиля SimPy выводит поток прибытий из `hourly_kwh / mean_session_kwh`. Не путать `hourly_kwh` (оценка отпущенной нагрузки по времени) с прибытием автомобилей. CSV без интервальных показаний счётчика даёт `hourly_load_method = uniform_session_duration`; показывать это как оценку.

## Подключение и основной поток

Браузер обращается к Next.js BFF, который передаёт `Authorization: Bearer <API_TOKEN>` в Go API. Токен не передавать в клиентский JavaScript. Локально Go API доступен по `http://localhost:58080/api/v1`; в Compose BFF обращается к `http://api:8080/api/v1`. Пароль веб-демо **не** равен проектной роли пользователя; многопользовательского RBAC пока нет.

1. `POST /api/v1/scenarios` с `{ "name": "...", "spec": PlanningInput }`. Go вызывает строгую валидацию Python, затем сохраняет неизменяемый снимок в PostgreSQL. Ответ `201 SavedScenario` с UUID и SHA‑256 **сохранённого JSONB-снимка**; хеш не обязан совпадать с хешем исходного текстового файла из-за нормализации JSON. При `422` показать `detail` рядом с полем или в панели ошибок, не запускать расчёт. `503` означает недоступность валидатора: не выдавать это за ошибку пользователя.
2. `GET /api/v1/scenarios` отдаёт до 100 последних снимков; `GET /api/v1/scenarios/{uuid}` возвращает полный снимок. Пока нет пагинации. Редактирование реализовывать как **новый** сценарий, не изменять уже сохранённый.
3. `POST /api/v1/scenarios/{uuid}/runs` с заголовком `Idempotency-Key` длиной 8–128 символов. Повтор с тем же ключом для этого сценария вернёт тот же run. Ответ `202 Run`.
4. `GET /api/v1/runs/{uuid}`: состояния `queued`, `running`, `succeeded`, `failed`, `cancelled`. `GET /api/v1/runs/{uuid}/events` — SSE; при повторном подключении передать `Last-Event-ID`. Polling `GET /runs/{uuid}` — резерв. Событие `queued` пока не записывается; поток начинается с `running`.
5. Только после `succeeded` получить `GET /api/v1/runs/{uuid}/results`. До этого `404 completed result not found`. `POST /api/v1/runs/{uuid}/cancel` возвращает `200` либо `409`, когда отмена уже невозможна.

`succeeded` означает, что вычислительный вызов завершился и результат сохранён. **Всегда проверять `result.optimization.status`:**

| Статус оптимизации | Представление |
|---|---|
| `optimal` | План на переданной области поиска; показывать `objective`, инвестиции, энергоаудит, качество данных |
| `feasible` | Допустимый план с остановкой по лимиту; показывать `gap` при наличии, не обещать оптимум |
| `infeasible` | Отдельное состояние «Ограничения несовместимы», `diagnostic`, без этапов строительства и метки успеха |
| `error` | Технический сбой расчёта; Run обычно `failed`, показывать `error_code`/`error_detail` и возможность повтора |

Нулевой `selected` при `optimal`/`feasible` может быть **правильным** решением оператора: строить нерентабельно при заданных условиях. Это не ошибка и не пустая загрузка.

## Что выводить из PlanResult

`optimization.selected[]` — `{site_id, option_id, year}`. `grid_upgrades[]` — `{grid_node_id, year, commissioned_year}`: `year` — год расхода бюджета, `commissioned_year` — первый год доступности дополнительной мощности. В `scenario.spec.grid_nodes[].upgrade_lead_years` указан срок ввода (по умолчанию 0). На временной шкале не включать усиление до `commissioned_year`. `battery[]`, `solar[]` — отдельные инвестиции. Идентификаторы сопоставлять с `scenario.spec`; названия и координаты брать из сохранённого снимка, не из встроенного демо.

`optimization.served_kwh`, `unmet_kwh`, `cashflow_rub` индексируются **ID сценария неопределённости**. Для `risk = expected_cvar` показывать `risk_metrics.cvar_alpha` и либо `cvar_loss_rub` (оператор), либо `cvar_unmet_kwh` (город). Вероятности должны быть заданы во входе и суммироваться до 1; UI не должен сам назначать вероятности.

`optimization.investment_rub_by_year[]` — год и CAPEX. `energy_audit[]` — по одной строке на площадку × год × сценарий: `served_kwh`, `grid_kwh`, `pv_used_kwh`, `pv_available_kwh`, `battery_charge_kwh`, `battery_discharge_kwh`, пиковые мощности и SoC на границах суток. `optimization.verification.passed` обязан быть `true` для допустимого плана; рядом доступны максимальные отклонения баланса, SoC, бюджета, сетевого узла и станции. Аудит ограничен 2000 строками: при `energy_audit_truncated = true` показывать, что подробные строки неполны. Это проверка ограничений модели, не AC power-flow.

`optimization.service_by_year[]` содержит для **каждой пары сценарий × год** `{scenario_id, year, demand_kwh, served_kwh, unmet_kwh}`; использовать эти строки для годового графика и проверки заявленной доли обслуживания. Они относятся к MILP, а не к числу завершённых сессий SimPy. В отличие от `energy_audit[]`, эти строки сейчас не усекаются.

`simulation[]` различается по `year`, `scenario_id`, `seed`. Отображать распределение по seed, а не выбирать один удачный запуск. `arrivals_by_hour[24]` показывает сгенерированные прибытия, `requested_energy_kwh` — суммарную энергию заявок, `energy_kwh` — реально отпущенную, `unserved_energy_kwh` — разность; `arrivals = served_sessions + refused_sessions`. `partial_energy_kwh` — уже отпущенная энергия в сессиях, не законченных до горизонта суток, она входит в `energy_kwh`, хотя сессия считается отказом. `dispatch_by_site[]` содержит `load_kwh` (отпущено автомобилям), `grid_kwh`, `pv_used_kwh`, `pv_curtailed_kwh`, `battery_charge_kwh`, `battery_discharge_kwh`, `battery_soc_start_kwh`, `battery_soc_end_kwh`; это итоги **событийной минутной** модели, их не подменять строками `optimization.energy_audit[]`. `dispatch_verification.passed` должен быть `true`: при нарушении расчёт не публикуется. Накопитель стартует пустым каждые моделируемые сутки и не получает заряд из будущего. Даже с наблюдёнными сессиями симулятор генерирует новые случайные прибытия по измеренному профилю: это модельная проверка, не точный replay и не доказательство годовой надёжности. `explanations[]` — контрфактический пересчёт без выбранной площадки, а не причинность в наблюдаемых данных.

`operational_validation[]` есть у основного плана и каждой альтернативы: по паре `{scenario_id, year}` он показывает долю обслуживания в MILP (`optimized_service_fraction`), среднюю/минимальную/максимальную долю в SimPy, `service_gap_percentage_points` (положительный разрыв означает оптимистичность почасовой модели), средние запрошенные/отпущенные/необслуженные кВт·ч и число `seeds`. Сравнивать именно **доли**, потому что случайная суммарная энергия заявок за сутки может отличаться от детерминированного профиля MILP. Это диагностический разрыв, автоматического пересчёта MILP по нему пока нет. При пустом списке seed массив пуст. `metadata.input_quality` содержит списки зон с наблюдённым/предположенным сессионным профилем или параметрическим потоком, `demand_scope` и предупреждения. Для `served_sessions_only` показывать явную подпись «история выполненных зарядок, скрытый необслуженный спрос неизвестен».

`operational_economics[]` также есть у основного и альтернативных планов: для каждого `scenario_id` показывает `optimized_npv_rub`, средний/минимальный/максимальный `simulated_npv_rub_*`, `optimism_gap_rub` и `profitability_sign_changed`. SimPy пересчитывает выручку из реально отпущенной энергии, покупку из `dispatch_by_site[].grid_kwh`, износ накопителя из `battery_discharge_kwh`, учитывает CAPEX и фиксированные расходы. При `profitability_sign_changed = true` выводить заметный риск экономического вывода. Обе экономики остаются экстраполяцией представительных суток × 365, а не фактическим годовым NPV.

### Альтернативы инвестиционного плана

В `PlanResult.alternatives[]` worker сейчас запрашивает три целевых уровня: `0`, `0.5`, `1`. Каждая запись имеет `target_service_fraction`, `achieved_min_service_fraction` (`null` для недопустимого плана), `objective_kind = minimum_investment_rub`, собственные `optimization` и `simulation[]`. `same_investment_as_target` — `null` для первой конфигурации или уровень другой записи с теми же площадками, усилениями, накопителями и PV; одинаковые инвестиции можно сгруппировать, но строки проверенных целей сохранить. Даже целевой уровень `0` может потребовать CAPEX из-за `minimum_zone_service` исходного сценария. В оптимизаторе доля обслуженной энергии должна быть достигнута **в каждом году и каждом сценарии неопределённости**, с сохранением всех бюджетных, физических и CVaR-ограничений исходного сценария. `optimization.objective` у альтернативы означает минимальный CAPEX в ₽; у основного плана смысл `objective` зависит от режима (`city` — обслуженная энергия, `operator` — NPV). Поэтому эти значения нельзя наносить на одну ось без преобразования.

Статус `infeasible` у уровня, например `1`, означает, что полное обслуживание при текущих кандидатах и бюджете невозможно; показывать его `diagnostic` и пустую симуляцию, не скрывать карточку. `feasible` означает допустимый план без доказанного минимума инвестиций: показывать `gap`, если он есть. Дополнительный расчёт ограничен 20 секундами решателя **на уровень**; сами уровни могут дать одинаковую инфраструктуру. Это сетка ε-ограничений, а не доказанный полный фронт Парето. Сравнивать CAPEX по `investment_rub_by_year`, обслуживание по `served_kwh`/`unmet_kwh`, экономику по `cashflow_rub`; симуляции сравнивать только для одинаковых `year`, `scenario_id`, `seed`. В метаданных есть `alternative_service_fractions` и `alternative_solver_seconds`.

## Карта и отдельные модели

- Базовая карта интерфейса использует **2ГИС MapGL**. `GET /api/maps/config` — внутренний маршрут Next.js BFF, после входа возвращает `{configured, apiKey?, styleId?}` из `DGIS_MAPGL_API_KEY` и необязательного `DGIS_MAP_STYLE_ID`. Этот веб-ключ виден браузеру; права на домены и Map Tiles API задаются у поставщика. Без ключа должен быть показан явный статус подключения. Координаты маркеров по-прежнему берутся из сохранённого `scenario.spec`, а не из карты 2ГИС.
- Для полностью динамического сценария сначала `POST /api/v1/datasets/import` (`multipart/form-data`: `file`, `name`, `kind`, `source`, опционально `license`, `captured_at`; дата обязательна при `kind=observed`). Ответ даёт **UUID версии**, число объектов и SHA-256. Затем `POST /api/v1/scenarios/from-datasets/preview` с четырьмя версиями в `dataset_versions`, поясом `time_zone`, оборудованием `options`, параметрами и сценариями неопределённости. Preview возвращает собранный `spec` и `data_quality`, не сохраняет данные; `POST /api/v1/scenarios/from-datasets` с тем же телом создаёт сценарий и возвращает `{scenario, data_quality}`. Использовать `scenario.id` для стандартного запуска. Точный формат четырёх слоёв и ошибки описаны в [DATASET_SCENARIOS.md](../DATASET_SCENARIOS.md); типы есть в OpenAPI. Даты, мощность и дорожные минуты не берутся из карты и не подставляются по умолчанию. `404` — выбранная версия отсутствует, `422` — недостаточные/несовместимые поля, `503` — валидатор недоступен. В форме сначала показывать preview и предупреждения `data_quality`, затем действие сохранения. Пометка `observed` — заявление источника; `options` и `parameters` отмечены как непроверенные допущения. Встроенный демо-JSON остаётся синтетическим.
- `GET /api/v1/datasets`: история импортированных версий геоданных с `checksum`, `license`, `captured_at` (если известна) и `created_at`. Повторный импорт тех же байтов с теми же именем, источником, типом, лицензией и временем наблюдения возвращает прежнюю версию; старые точные дубликаты в истории сохраняются, но карта их не дублирует. `GET /api/v1/map?bbox=west,south,east,north&type=...`: GeoJSON, максимум 1000 объектов за запрос. `GET /api/v1/tiles/{z}/{x}/{y}?type=...`: MVT из PostGIS, кэш Redis с TTL 30 секунд и чтение из БД при отказе Redis. Разные версии с изменённым содержимым или происхождением пока могут сосуществовать на карте; селектор конкретной версии ещё не предусмотрен. Карта объединяет версии для отображения, а сборка расчёта использует только четыре явно выбранных UUID. При сопоставлении объектов показывать происхождение каждого слоя и не переносить численные значения молча.
- `POST /api/v1/corridors/check`: отдельная модель достижимости с отказом каждой станции; вход `CorridorSpec`, ответ `reachable`, `stops`, `legs`, `station_failure_impacts`, `assumptions`. Позиции станций должны уже соответствовать дорожному маршруту.
- `POST /api/v1/fleets/schedule`: отдельная MILP-модель парка; вход `FleetSpec`, ответ `status`, `schedule`, `peak_kw`, `trip_ids_served`, `end_energy_kwh`, `assumptions`. GTFS преобразуется **бэкенд CLI-адаптером** с отдельными назначениями машин, энергией рейсов и окнами зарядки. Не принимать GTFS-файл за готовый `FleetSpec` в браузере.

## Конкретные задачи фронтенда

1. Генерировать типы из `openapi.json` в CI и убрать ручные частичные типы для `PlanResult`/`ScenarioSpec`, сохранив runtime-проверку внешнего ответа. Схема результата должна обрабатывать `null`, пустые массивы, `infeasible` и `feasible`.
2. Разнести состояния задачи и оптимизации, вывести `diagnostic`, `gap`, `verification`, годы CAPEX и энергоаудит. Никакого общего «успеха» по одному лишь `Run.state`.
3. Сделать полноценный редактор допущений и происхождения с единицами, источником, датой наблюдения и валидацией диапазонов до отправки. Отмечать синтетический и наблюдаемый ввод по каждому объекту.
   Для загрузки нормализованных слоёв добавить выбор четырёх UUID версий, preview и сообщения `data_quality`. Не отображать карту как единственный источник численных полей расчёта.
4. Вывести `alternatives[]` рядом с основным планом как таблицу «уровень обслуживания → CAPEX → обслуженная энергия → NPV → статус/очередь». Для каждой строки показать `operational_validation` и предупреждения `metadata.input_quality` основного входа: если фактическая доля SimPy ниже расчётной, не скрывать разрыв за статусом `optimal`. Сопоставлять одинаковые сценарии, годы и seed; показывать, какой показатель основан на MILP, какой — на SimPy, и какая часть ещё не подтверждена инженерно. Не подписывать `feasible` как доказанный минимум и не скрывать `infeasible`.
5. Добавить UI коридора и парка только на реальные контракты выше; состояние «нет назначений/энергии/техусловий» должно быть явным, без подстановки демо.
6. Покрыть E2E сценарии `feasible`, `infeasible`, пустого экономического плана, ошибок `422/503`, отмены и повторного подключения SSE. Пароль и API token не должны попадать в клиентский bundle или логи.

Сейчас фронтенд умеет загрузить полный пользовательский JSON и выполнить основной расчёт, но перечисленные специализированные представления и полный аудит ещё не реализованы. Бэкенд-развитие не следует имитировать статическими карточками: каждый показатель должен ссылаться на конкретное поле результата и входной снимок.
