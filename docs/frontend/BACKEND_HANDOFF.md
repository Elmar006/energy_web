# Контракт бэкенда для фронтенда

Актуально для ветки `backend/algo`. Машинный контракт — [`openapi.json`](../../openapi.json); этот документ описывает пользовательские состояния и границы уже работающих вычислений. При изменении API обновлять оба файла в том же PR. Фронтенд здесь не меняется: это ТЗ на его следующую интеграцию.

**Правило интеграции:** используйте фактический контракт ниже и [OpenAPI](../../openapi.json); планируемые изменения отделены в [ROADMAP.md](../ROADMAP.md). Сохраняемый RunSpec, сценарная приёмка обслуживания и предварительное построение потенциального спроса из маршрутов уже доступны. Каждая следующая поставка бэкенда должна включать обновление этого документа, совместимость старых ответов и состояния ошибок для фронтенда.

## Данные и доверие

- Встроенный пример — **синтетический**. Координаты и реальные дороги OSRM не делают спрос или резерв электросети наблюдаемыми.
- Поле `provenance.kind` у зоны, площадки и узла: `observed` (заявлено как наблюдение), `derived` (вычислено из источника), `assumed` (сценарное допущение). Показывать `source`; `observed` сейчас не означает независимую проверку платформой.
- `datasets[]` фиксирует источник, SHA‑256, роль, вид данных и при наличии лицензию. Пустое значение нельзя рисовать как ноль.
- Величины: энергия — кВт·ч, мощность — кВт, деньги — ₽, расстояние — км, время маршрута — минуты. `investment_rub_by_year` — CAPEX по календарному году; `cashflow_rub` — сценарная дисконтированная экономика типовых суток либо короткого датированного горизонта с явным `annualization_factor`, а не заключение о фактической окупаемости.
- `optimal` относится **только к переданным площадкам, сценариям и временной сетке**. Отсутствует AC power-flow и подтверждение техусловий присоединения; интерфейс не должен маркировать план «сетевой экспертизой».
- `scenario.spec.zones[].arrival_profile` появляется после импорта CSV сессий или в подготовленном наборе зон: `hourly_sessions[24]` — среднее число **начатых** сессий в локальный час за сутки, `hourly_count_variance[24]` — выборочная дисперсия суточного числа, `energy_quantiles_kwh[101]` — квантили 0–100%, `sample_count`, `observation_days`, `days_with_sessions`, `coverage_complete`, `source_kind`, `hourly_load_method`, `provenance`. `coverage_complete` — заявка загрузившего о полноте выгрузки по всем зонам и дням; отсутствие строк в день без неё приводит к `422`, а не к нулевому спросу. При отсутствии профиля SimPy выводит поток прибытий из `hourly_kwh / mean_session_kwh`. Не путать `hourly_kwh` (оценка отпущенной нагрузки по времени) с прибытием автомобилей. CSV без интервальных показаний счётчика даёт `hourly_load_method = uniform_session_duration`; показывать это как оценку.

### Спрос из мобильности: новый предварительный расчёт

`POST /api/v1/scenarios/from-mobility/preview` принимает `{ "input": ScenarioSpec, "mobility": MobilityInput }` размером до 4 МиБ и возвращает `200 PreparedMobilityScenario`: `spec` (новый, **ещё не сохранённый** расчётный вход), `requests[]` (возможные публичные зарядки с окном и энергией), разреженные `calendar_profiles[]`, `audit`, `source_sha256`, `source_canonical_json`, `compiler_source_sha256` и `compiler_pydantic_version`. В `spec.datasets[]` записаны `kind=derived` и отдельное `source_kind=observed|assumed` для заявленного происхождения маршрутов. Предпочтительный путь сохранения — `POST /api/v1/scenarios/from-mobility` с `{name,input,mobility}`: он атомарно сохраняет расчётный сценарий и исходные маршруты, возвращает `201 SavedMobilityScenario` с UUID версии и одноразовым `source_access_token`. Затем запускайте обычный `/runs`. Обычный `POST /api/v1/scenarios` сохранит только `spec`, без исходника маршрутов.

Для восстановления исходного входа используйте `GET /api/v1/scenarios/{id}/mobility-origin` с обычным bearer и `X-Mobility-Source-Token: <source_access_token>`. Capability показывается только при создании: храните его на серверной стороне или передайте пользователю безопасным способом один раз; не кладите в браузерный bundle, URL или логи. Без capability ответ `404`, даже если сценарий существует. Проекты/RBAC ещё не реализованы: capability защищает исходные траектории, но не изолирует остальные результаты между командами. Отдельные `requests[]` и календарь остаются результатом preview, а не реестром исполнения.

Форма должна требовать **явно выбранные** `covered_dates`, `replace_zone_ids`, IANA `time_zone`, источник и `source_kind`; для каждой машины — сегмент, ёмкость/начальный и резервный заряд, расход на км, КПД, вес в популяции и его текстовое основание при весе не равном 1, чередование поездок и стоянок, доступ частной/публичной зарядки. Показывайте кВт·ч, кВт, км и время с UTC-смещением; при `422 invalid_mobility` сохраняйте форму и выводите `detail`. `400` — JSON, `413` — размер, `502` — некорректный ответ вычислителя, `503` — временная недоступность. Отклонённая поездка не превращается в нулевой спрос.

Подпись интерфейса: «Потенциальные заявки из переданных маршрутов; публичная зарядка условно учтена при проверке возможности последующих поездок». В `requests[]` прибытие может быть позже начала стоянки, если сначала использовалась частная зарядка. `spec.service_calendar` и `spec.charging_requests[]` **управляют датированным расчётом** оптимизатора и SimPy; `calendar_profiles[]` остаётся обзорным представлением для интерфейса. Не выбранные в `replace_zone_ids` зоны явно сохраняют прежний повторяемый профиль. Никакого статуса «реальный прогноз» по `source_kind=observed` или по `accepted` выдавать нельзя. Образец и ограничения — в [MOBILITY_DEMAND.md](../MOBILITY_DEMAND.md) и [DATED_DEMAND.md](../DATED_DEMAND.md).

### Датированные заявки, артефакты и отдельная итоговая проверка

Для ручной загрузки датированного спроса пользователь сначала задаёт `service_calendar` (IANA-пояс, 1–14 **последовательных** покрытых дней, явные `request_zone_ids` и `legacy_profile_zone_ids`, `annualization_factor` и `annualization_basis=assumed_repeat`). Все зоны сценария должны попасть ровно в один режим. В каждой заявке показывайте зону/сегмент, прибытие, дедлайн, энергию **от поста** в кВт·ч, КПД, SoC, мощность автомобиля, вес и provenance. Отсутствующий день при заявленном полном покрытии не приравнивайте молча к нулю. Датированные зоны используют заявки в оптимизации и SimPy; профильные зоны продолжают повторять 24 часа. UI должен показывать короткий охват и предположенный множитель годовой экстраполяции рядом с NPV.

Малый набор можно передать inline в `POST /api/v1/scenarios` через `spec.service_calendar` + `spec.charging_requests`. Для большого набора проведите **через серверный BFF** сырой JSON-документ `demand-dataset-v1` на `POST /api/v1/artifacts/demand` (предел 64 МиБ). Ответ `201 DemandDataset` содержит `schema_version`, `artifact_id=sha256:<hex>`, `sha256`, `byte_size`. Далее создайте сценарий со **только** `spec.demand_dataset = <полный манифест>`; вместе с ним inline `service_calendar`/`charging_requests` отправлять нельзя. Токен Go API остаётся на сервере. В этом контракте нет произвольного URL и нет маршрута скачивания артефакта для браузера. `413 artifact_too_large` — размер, `422 invalid_demand_artifact` — форма JSON; недоступный локальный store при upload даёт `503 artifact_store_unavailable`. Сохранённый сценарий хранит ссылку, worker сверяет SHA-256 перед engine; при утрате файла повтор невозможен. Пока это локальный volume, не S3 и не проектное хранилище с RBAC.

`run-spec-v2` включается явным `schema_version`. Для ограниченного пересчёта нужны `mode=validation`, `service_requirements`, `development_seeds` (2–30) и `max_improvement_iterations` (1–3); итоговые `simulation_seeds` — **не менее 30** и не пересекаются с разработочными. `result.improvement.iterations[]` показывает найденные кандидаты, статусы, разработочный score и `selected_for_holdout`. `service_acceptance` по-прежнему относится только к итоговым seed. Интерфейс должен назвать разработочный score «подбор варианта на сценарных потоках», а `accepted` — «пройден заданный порог на итоговых сценарных потоках»; ни один не подтверждает реальный городской спрос. Старый `run-spec-v1` и вызов без тела сохраняются. Полные диапазоны, коды ошибок и пример — в [RUN_SPEC.md](../RUN_SPEC.md) и OpenAPI.

## Подключение и основной поток

**Настройки запуска:** `POST /api/v1/scenarios/{uuid}/runs` принимает необязательное тело `{ "run_spec": {...} }`; без тела поведение остаётся прежним. Текущие поля, диапазоны и пример — в [RUN_SPEC.md](../RUN_SPEC.md) и OpenAPI. Ответ `Run` содержит полностью разрешённый `run_spec`, хеши исходного сценария, настроек и исполнения, а также `run_spec_origin=resolved|legacy_inferred`. Для оценки сервиса отправляйте `mode=validation`, минимум 30 seed и `service_requirements` из [контракта приёмки](../SERVICE_ACCEPTANCE.md). Основной и альтернативные планы возвращают `service_acceptance.status`: `accepted` — пороги пройдены **в сценарной симуляции**, `rejected` — порог/физическое ограничение нарушено, `inconclusive` — данных недостаточно или интервал пересёк порог, `not_evaluated` — пороги не заданы. Показывайте причины и строки `conditions[]` по каждому году/сценарию; не обозначайте `accepted` как подтверждение реального города. Повтор ключа с другим телом — `409 idempotency_conflict`; неверные параметры — `422 invalid_run_spec`, запрос более 16 КиБ — `413`.

Браузер обращается к Next.js BFF, который передаёт `Authorization: Bearer <API_TOKEN>` в Go API. Токен не передавать в клиентский JavaScript. Локально Go API доступен по `http://localhost:58080/api/v1`; в Compose BFF обращается к `http://api:8080/api/v1`. Пароль веб-демо **не** равен проектной роли пользователя; многопользовательского RBAC пока нет.

1. `POST /api/v1/scenarios` с `{ "name": "...", "spec": PlanningInput }`. Go вызывает строгую валидацию Python, затем сохраняет неизменяемый снимок в PostgreSQL. Ответ `201 SavedScenario` с UUID и SHA‑256 **сохранённого JSONB-снимка**; хеш не обязан совпадать с хешем исходного текстового файла из-за нормализации JSON. При `422` показать `detail` рядом с полем или в панели ошибок, не запускать расчёт. `503` означает недоступность валидатора: не выдавать это за ошибку пользователя.
2. `GET /api/v1/scenarios` отдаёт до 100 последних снимков; `GET /api/v1/scenarios/{uuid}` возвращает полный снимок. Пока нет пагинации. Редактирование реализовывать как **новый** сценарий, не изменять уже сохранённый.
3. `POST /api/v1/scenarios/{uuid}/runs` с заголовком `Idempotency-Key` длиной 8–128 символов. Повтор с тем же ключом для этого сценария вернёт тот же run. Ответ `202 Run`.
4. `GET /api/v1/runs/{uuid}`: состояния `queued`, `running`, `succeeded`, `failed`, `cancelled`. `GET /api/v1/runs/{uuid}/events` — SSE; при повторном подключении передать `Last-Event-ID`. Polling `GET /runs/{uuid}` — резерв. Событие `queued` пока не записывается; поток начинается с `running`.
5. Только после `succeeded` получить `GET /api/v1/runs/{uuid}/results`. До этого `404 completed result not found`. `POST /api/v1/runs/{uuid}/cancel` возвращает `200` либо `409`, когда отмена уже невозможна.

### Прямая загрузка CSV для расчёта

Теперь вместо локальной CLI-подготовки JSON можно вызвать `POST /api/v1/scenarios/{parent_id}/imports/sessions` или `POST /api/v1/scenarios/{parent_id}/imports/grid-headroom` с `multipart/form-data`. Строгая схема обоих запросов есть в OpenAPI; примеры и смысл полей — в [DIRECT_UPLOAD.md](../DIRECT_UPLOAD.md). Обязательны `scenario_name` (название нового сценария), `dataset_name` (название версии файла), `source`, `kind=observed|assumed`, `time_zone`, `file`. Для сессий дополнительно `start_date`, `end_date`; для сети — `profile_date`. `license` опциональна. Сессионное поле `coverage_complete=true|false` задаётся только при подтверждённой полноте всего интервала: UI должен объяснить, что пустые дни считаются реальными нулями **только** при `true`. Максимум 50 МиБ для сессий и 10 МиБ для сети.

Ответ `201 PlanningCSVImportResult` содержит **новый** `scenario` с полным `spec`, `dataset_id`, SHA-256 исходного CSV, `role` и `reused`. В `scenario.spec.datasets[]` есть `version_id` и `transform_version` применённого адаптера. Для сетевого CSV роль импорта и каталога — `grid_headroom`, а роль того же набора в `scenario.spec.datasets[]` — `grid`. Новую загрузку сетевого профиля направлять на `scenario.id` после загрузки сессий, чтобы обе версии вошли в один снимок. Для расчёта использовать последний `scenario.id` с обычным `POST /runs`; импорт сам не запускает solver. Идентичный повтор к тому же родительскому сценарию, версии преобразования и метаданным вернёт `reused=true` и прежний сценарий. Исходный `parent_id` не меняется.

Страница ввода должна сначала показывать соответствие `zone_id` или `grid_node_id` из выбранного сценария колонкам CSV, единицы, интервал и предупреждение о том, что `observed` — заявление поставщика. Перед отправкой выводить явный выбор нового имени сценария и источника; не присваивать статус `observed` автоматически. На `422 invalid_import` показывать `detail` и сохранять форму/файл для исправления; `404` — родитель удалён/не найден; `413` — превышение размера; `503` — временно недоступен вычислительный сервис, безопасен повтор. После `201` показать версии в `GET /api/v1/datasets` (`format="csv"`, `role`) и кнопку проверки/скачивания `GET /api/v1/datasets/{dataset_id}/file`. Этот запрос возвращает точные байты исходного CSV и `X-Content-SHA256`; файлы реальных сессий могут быть конфиденциальными. Next.js BFF должен проксировать upload/download с серверным `API_TOKEN`, не передавать токен браузеру и не логировать CSV.

Загрузка сессий заменяет выполненный профиль энергии и создаёт `arrival_profile`; она **не** раскрывает скрытый необслуженный спрос. Загрузка `headroom_kw` задаёт доступный резерв, а не подтверждает полную электрическую схему. Экран результата уже показывает предупреждения `metadata.input_quality` и разрыв `operational_validation`, но отдельная форма CSV-загрузки и вывод `operational_economics` для всех альтернатив остаются задачами фронтенда. API готов для прямого вызова.

`succeeded` означает, что вычислительный вызов завершился и результат сохранён. **Всегда проверять `result.optimization.status`:**

| Статус оптимизации | Представление |
|---|---|
| `optimal` | План на переданной области поиска; показывать `objective`, инвестиции, энергоаудит, качество данных |
| `feasible` | Допустимый план с остановкой по лимиту; показывать `gap` при наличии, не обещать оптимум |
| `infeasible` | Отдельное состояние «Ограничения несовместимы», `diagnostic`, без этапов строительства и метки успеха |
| `error` | Технический сбой расчёта; Run обычно `failed`, показывать `error_code`/`error_detail` и возможность повтора |

Нулевой `selected` при `optimal`/`feasible` может быть **правильным** решением оператора: строить нерентабельно при заданных условиях. Это не ошибка и не пустая загрузка.

## Что выводить из PlanResult

`optimization.selected[]` — `{site_id, option_id, year}`. `grid_upgrades[]` — `{grid_node_id, year, commissioned_year}`: `year` — год расхода бюджета, `commissioned_year` — первый год доступности дополнительной мощности. В `scenario.spec.grid_nodes[].upgrade_lead_years` указан срок ввода (по умолчанию 0). На временной шкале не включать усиление до `commissioned_year`. `battery[]`, `solar[]` — отдельные инвестиции. Идентификаторы сопоставлять с `scenario.spec`; названия и координаты брать из сохранённого снимка, не из встроенного демо.

`optimization.served_kwh`, `unmet_kwh`, `cashflow_rub` индексируются **ID сценария неопределённости**. Для `risk = expected_cvar` показывать `risk_metrics.cvar_alpha` и либо `cvar_loss_rub` (оператор), либо `cvar_unmet_kwh` (город). Вероятности должны быть заданы во входе и суммироваться до 1; UI не должен сам назначать вероятности.

`optimization.investment_rub_by_year[]` — год и CAPEX. `energy_audit[]` — по одной строке на площадку × год × сценарий: `served_kwh`, `grid_kwh`, `pv_used_kwh`, `pv_available_kwh`, `battery_charge_kwh`, `battery_discharge_kwh`, пиковые мощности и SoC на границах суток. `optimization.verification.passed` обязан быть `true` для допустимого плана; рядом доступны максимальные отклонения баланса, SoC, бюджета, сетевого узла и станции. Аудит ограничен 2000 строками: при `energy_audit_truncated = true` показывать, что подробные строки неполны. Это проверка ограничений модели, не AC power-flow.

`optimization.service_by_year[]` содержит для **каждой пары сценарий × год** `{scenario_id, year, demand_kwh, served_kwh, unmet_kwh}`; использовать эти строки для годового графика и проверки заявленной доли обслуживания. Они относятся к MILP, а не к числу завершённых сессий SimPy. В отличие от `energy_audit[]`, эти строки сейчас не усекаются.

`simulation[]` различается по `year`, `scenario_id`, `seed`; `simulation_days` берётся из сохранённого `run.run_spec.simulation_days` (1–14; без переопределения наследуется из `scenario.spec.parameters`). Отображать распределение по seed, а не выбирать один удачный запуск. `arrivals_by_hour[24]` и объёмы `requested_energy_kwh`, `energy_kwh`, `unserved_energy_kwh` — **суммы за весь горизонт**, не за сутки; `arrivals_by_day_hour[][]` и `day_dispatch[]` показывают дни отдельно. `arrivals = served_sessions + refused_sessions`. `partial_energy_kwh` — отпущенная энергия сессий, не законченных до **конца всего горизонта**. `dispatch_by_site[]` содержит суммарные `load_kwh`, `grid_kwh`, `pv_used_kwh`, `pv_curtailed_kwh`, `battery_charge_kwh`, `battery_discharge_kwh`, `battery_soc_start_kwh`, `battery_soc_end_kwh`; `day_dispatch[].dispatch_by_site[]` — те же потоки и SoC на границе каждого дня. `day_dispatch[].charging_sessions_at_boundary` и `queued_sessions_at_boundary` позволяют видеть перенос нагрузки через полночь. `dispatch_verification.passed` включает баланс накопителя и должен быть `true`; при нарушении расчёт не публикуется. Накопитель стартует пустым **только в начале всего горизонта**, переносит заряд на следующий день и не получает заряд из будущего. Даже с наблюдёнными сессиями симулятор генерирует новые случайные прибытия по одному повторяющемуся суточному профилю: это модельная проверка, не точный replay и не доказательство годовой надёжности. `explanations[]` — контрфактический пересчёт без выбранной площадки.

`operational_validation[]` есть у основного плана и каждой альтернативы: по паре `{scenario_id, year}` он показывает долю обслуживания в MILP (`optimized_service_fraction`), среднюю/минимальную/максимальную долю в SimPy, `service_gap_percentage_points` (положительный разрыв означает оптимистичность почасовой модели), средние запрошенные/отпущенные/необслуженные **кВт·ч в сутки**, число `seeds` и `simulation_days`. Сравнивать именно **доли**, потому что случайная суммарная энергия заявок может отличаться от детерминированного профиля MILP. По умолчанию это диагностический разрыв; opt-in `run-spec-v2` может до трёх раз пересчитать план с дополнительной площадкой на отдельных seed разработки и проверить выбранный вариант на итоговых seed. При пустом списке seed массив пуст. `metadata.input_quality` содержит списки зон с наблюдённым/предположенным сессионным профилем или параметрическим потоком, `unverified_coverage_zone_ids`, `claimed_complete_coverage_zone_ids`, `demand_scope` и предупреждения. Для `served_sessions_only` показывать явную подпись «история выполненных зарядок, скрытый необслуженный спрос неизвестен».

`operational_economics[]` также есть у основного и альтернативных планов: для каждого `scenario_id` показывает `optimized_npv_rub`, средний/минимальный/максимальный `simulated_npv_rub_*`, `optimism_gap_rub` и `profitability_sign_changed`. SimPy пересчитывает выручку из реально отпущенной энергии, покупку из `dispatch_by_site[].grid_kwh`, износ накопителя из `battery_discharge_kwh`, учитывает CAPEX и фиксированные расходы. При `profitability_sign_changed = true` выводить заметный риск экономического вывода. Обе экономики остаются экстраполяцией короткого горизонта: типовые сутки × 365 либо датированный период × `annualization_factor`, а не фактическим годовым NPV.

### Альтернативы инвестиционного плана

В `PlanResult.alternatives[]` worker сейчас запрашивает три целевых уровня: `0`, `0.5`, `1`. Каждая запись имеет `target_service_fraction`, `achieved_min_service_fraction` (`null` для недопустимого плана), `objective_kind = minimum_investment_rub`, собственные `optimization` и `simulation[]`. `same_investment_as_target` — `null` для первой конфигурации или уровень другой записи с теми же площадками, усилениями, накопителями и PV; одинаковые инвестиции можно сгруппировать, но строки проверенных целей сохранить. Даже целевой уровень `0` может потребовать CAPEX из-за `minimum_zone_service` исходного сценария. В оптимизаторе доля обслуженной энергии должна быть достигнута **в каждом году и каждом сценарии неопределённости**, с сохранением всех бюджетных, физических и CVaR-ограничений исходного сценария. `optimization.objective` у альтернативы означает минимальный CAPEX в ₽; у основного плана смысл `objective` зависит от режима (`city` — обслуженная энергия, `operator` — NPV). Поэтому эти значения нельзя наносить на одну ось без преобразования.

Статус `infeasible` у уровня, например `1`, означает, что полное обслуживание при текущих кандидатах и бюджете невозможно; показывать его `diagnostic` и пустую симуляцию, не скрывать карточку. `feasible` означает допустимый план без доказанного минимума инвестиций: показывать `gap`, если он есть. Дополнительный расчёт ограничен 20 секундами решателя **на уровень**; сами уровни могут дать одинаковую инфраструктуру. Это сетка ε-ограничений, а не доказанный полный фронт Парето. Сравнивать CAPEX по `investment_rub_by_year`, обслуживание по `served_kwh`/`unmet_kwh`, экономику по `cashflow_rub`; симуляции сравнивать только для одинаковых `year`, `scenario_id`, `seed`. В метаданных есть `alternative_service_fractions` и `alternative_solver_seconds`.

## Карта и отдельные модели

- Базовая карта интерфейса использует **2ГИС MapGL**. `GET /api/maps/config` — внутренний маршрут Next.js BFF, после входа возвращает `{configured, apiKey?, styleId?}` из `DGIS_MAPGL_API_KEY` и необязательного `DGIS_MAP_STYLE_ID`. Этот веб-ключ виден браузеру; права на домены и Map Tiles API задаются у поставщика. Без ключа должен быть показан явный статус подключения. Координаты маркеров по-прежнему берутся из сохранённого `scenario.spec`, а не из карты 2ГИС.
- Для полностью динамического сценария сначала `POST /api/v1/datasets/import` (`multipart/form-data`: `file`, `name`, `kind`, `source`, опционально `license`, `captured_at`; дата обязательна при `kind=observed`). Ответ даёт **UUID версии**, число объектов и SHA-256. Затем `POST /api/v1/scenarios/from-datasets/preview` с четырьмя версиями в `dataset_versions`, поясом `time_zone`, оборудованием `options`, параметрами и сценариями неопределённости. Preview возвращает собранный `spec` и `data_quality`, не сохраняет данные; `POST /api/v1/scenarios/from-datasets` с тем же телом создаёт сценарий и возвращает `{scenario, data_quality}`. Использовать `scenario.id` для стандартного запуска. Точный формат четырёх слоёв и ошибки описаны в [DATASET_SCENARIOS.md](../DATASET_SCENARIOS.md); типы есть в OpenAPI. Даты, мощность и дорожные минуты не берутся из карты и не подставляются по умолчанию. `404` — выбранная версия отсутствует, `422` — недостаточные/несовместимые поля, `503` — валидатор недоступен. В форме сначала показывать preview и предупреждения `data_quality`, затем действие сохранения. Пометка `observed` — заявление источника; `options` и `parameters` отмечены как непроверенные допущения. Встроенный демо-JSON остаётся синтетическим.
- `GET /api/v1/datasets`: история импортированных версий геоданных с `checksum`, `license`, `captured_at` (если известна) и `created_at`. Повторный импорт тех же байтов с теми же именем, источником, типом, лицензией и временем наблюдения возвращает прежнюю версию; старые точные дубликаты в истории сохраняются, но карта их не дублирует. `GET /api/v1/map?bbox=west,south,east,north&type=...`: GeoJSON, максимум 1000 объектов за запрос. `GET /api/v1/tiles/{z}/{x}/{y}?type=...`: MVT из PostGIS, кэш Redis с TTL 30 секунд и чтение из БД при отказе Redis. Разные версии с изменённым содержимым или происхождением пока могут сосуществовать на карте; селектор конкретной версии ещё не предусмотрен. Карта объединяет версии для отображения, а сборка расчёта использует только четыре явно выбранных UUID. При сопоставлении объектов показывать происхождение каждого слоя и не переносить численные значения молча.
- `POST /api/v1/corridors/check`: отдельная модель достижимости с отказом каждой станции; вход `CorridorSpec`, ответ `reachable`, `stops`, `legs`, `station_failure_impacts`, `assumptions`. Позиции станций должны уже соответствовать дорожному маршруту.
- `POST /api/v1/fleets/schedule`: отдельная MILP-модель парка; вход `FleetSpec`, ответ `status`, `schedule`, `peak_kw`, `trip_ids_served`, `end_energy_kwh`, `assumptions`. GTFS преобразуется **бэкенд CLI-адаптером** с отдельными назначениями машин, энергией рейсов и окнами зарядки. Не принимать GTFS-файл за готовый `FleetSpec` в браузере.

## Конкретные задачи фронтенда

Для маршрутов в `result.metadata.input_quality` проверять `mobility_derived_zone_ids` и `mobility_sources`; значение `demand_scope=mobility_potential` означает потенциальную публичную потребность из предоставленных поездок, а не наблюдённый городской спрос. При смешанных источниках будет `demand_scope=mixed`.

В `GET /api/v1/datasets` сохранённый источник маршрутов имеет `format=mobility`, `role=mobility_source`; не пытайтесь открыть его как GeoJSON или CSV. Сам исходник доступен только через `mobility-origin` с отдельным capability.

1. Генерировать типы из `openapi.json` в CI и убрать ручные частичные типы для `PlanResult`/`ScenarioSpec`, сохранив runtime-проверку внешнего ответа. Схема результата должна обрабатывать `null`, пустые массивы, `infeasible` и `feasible`.
2. Разнести состояния задачи и оптимизации, вывести `diagnostic`, `gap`, `verification`, годы CAPEX и энергоаудит. Никакого общего «успеха» по одному лишь `Run.state`.
3. Сделать полноценный редактор допущений и происхождения с единицами, источником, датой наблюдения и валидацией диапазонов до отправки. Отмечать синтетический и наблюдаемый ввод по каждому объекту.
   Для загрузки нормализованных слоёв добавить выбор четырёх UUID версий, preview и сообщения `data_quality`. Не отображать карту как единственный источник численных полей расчёта.
   Для мобильности добавить отдельный предварительный экран ввода маршрутов и результата `requests[]`/`audit`; выводить заявленное покрытие дат и пояснение, что `hourly_kwh` — только совместимый средний контроль, тогда как расчёт использует заявки и их окна. Кнопка сохранения должна отправлять исходные `input` и `mobility` на сохраняющий маршрут, а не пересчитывать спрос в браузере; после ответа обеспечить сохранение одноразового capability.
4. Вывести `alternatives[]` рядом с основным планом как таблицу «уровень обслуживания → CAPEX → обслуженная энергия → NPV → статус/очередь». Для каждой строки показать `operational_validation` и предупреждения `metadata.input_quality` основного входа: если фактическая доля SimPy ниже расчётной, не скрывать разрыв за статусом `optimal`. Сопоставлять одинаковые сценарии, годы и seed; показывать, какой показатель основан на MILP, какой — на SimPy, и какая часть ещё не подтверждена инженерно. Не подписывать `feasible` как доказанный минимум и не скрывать `infeasible`.
5. Добавить UI коридора и парка только на реальные контракты выше; состояние «нет назначений/энергии/техусловий» должно быть явным, без подстановки демо.
6. Покрыть E2E сценарии `feasible`, `infeasible`, пустого экономического плана, ошибок `422/503`, отмены и повторного подключения SSE. Пароль и API token не должны попадать в клиентский bundle или логи.

Для новой поставки отдельно нужны: BFF-upload `demand-dataset-v1` без раскрытия bearer и с прогрессом/ошибкой 64 МиБ; форма календаря/заявок с явным происхождением и предпросмотром зон в двух режимах; переключатель `run-spec-v1/v2` с валидацией пересечения seed; история `result.improvement` и раздельные состояния математической допустимости, разработочного подбора и итоговой приёмки. До реализации UI API можно проверить напрямую по [DATED_DEMAND.md](../DATED_DEMAND.md). Не показывайте новые поля как уже введённые формы текущего интерфейса.

Сейчас фронтенд умеет загрузить полный пользовательский JSON, выполнить расчёт и показать таблицу основного плана/альтернатив с CAPEX, долей SimPy и разрывом MILP–SimPy, предупреждения качества входа, сводку проверки энергии и посуточные потоки. Эти блоки читают поля текущего ответа, а не статические карточки. **Ещё нужны** формы мобильности и импорта CSV/четырёх нормализованных наборов, интервалы по seed и экономика каждой альтернативы, подробный почасовой аудит, управление версиями, специализированные экраны парка/коридора и тесты состояний из пунктов выше. В таблице альтернатив сейчас показан только выбранный сценарий и первый год; не переносить эту строку на весь горизонт без явной подписи.
