# Контракт бэкенда для фронтенда

Актуально для ветки `backend/algo`. Машинный контракт — [`openapi.json`](../../openapi.json); этот документ описывает пользовательские состояния и границы уже работающих вычислений. При изменении API обновлять оба файла в том же PR. Фронтенд здесь не меняется: это ТЗ на его следующую интеграцию.

## Данные и доверие

- Встроенный пример — **синтетический**. Координаты и реальные дороги OSRM не делают спрос или резерв электросети наблюдаемыми.
- Поле `provenance.kind` у зоны, площадки и узла: `observed` (заявлено как наблюдение), `derived` (вычислено из источника), `assumed` (сценарное допущение). Показывать `source`; `observed` сейчас не означает независимую проверку платформой.
- `datasets[]` фиксирует источник, SHA‑256, роль, вид данных и при наличии лицензию. Пустое значение нельзя рисовать как ноль.
- Величины: энергия — кВт·ч, мощность — кВт, деньги — ₽, расстояние — км, время маршрута — минуты. `investment_rub_by_year` — CAPEX по календарному году; `cashflow_rub` — сценарная дисконтированная экономика представительных суток, а не заключение о фактической окупаемости.
- `optimal` относится **только к переданным площадкам, сценариям и временной сетке**. Отсутствует AC power-flow и подтверждение техусловий присоединения; интерфейс не должен маркировать план «сетевой экспертизой».

## Подключение и основной поток

Браузер обращается к Next.js BFF, который передаёт `Authorization: Bearer <API_TOKEN>` в Go API. Токен не передавать в клиентский JavaScript. Локально Go API доступен по `http://localhost:58080/api/v1`; в Compose BFF обращается к `http://api:8080/api/v1`. Пароль веб-демо **не** равен проектной роли пользователя; многопользовательского RBAC пока нет.

1. `POST /api/v1/scenarios` с `{ "name": "...", "spec": PlanningInput }`. Go вызывает строгую валидацию Python, затем сохраняет неизменяемый снимок в PostgreSQL. Ответ `201 SavedScenario` с UUID и SHA‑256 **сохранённого JSONB-снимка**; хеш не обязан совпадать с хешем исходного текстового файла из-за нормализации JSON. При `422` показать `detail` рядом с полем или в панели ошибок, не запускать расчёт. `503` означает недоступность валидатора: не выдавать это за ошибку пользователя.
2. `GET /api/v1/scenarios` отдаёт до 100 последних снимков; `GET /api/v1/scenarios/{uuid}` возвращает полный снимок. Пока нет пагинации. Редактирование реализовывать как **новый** сценарий, не изменять уже сохранённый.
3. `POST /api/v1/scenarios/{uuid}/runs` с заголовком `Idempotency-Key` длиной 8–128 символов. Повтор с тем же ключом для этого сценария вернёт тот же run. Ответ `202 Run`.
4. `GET /api/v1/runs/{uuid}`: состояния `queued`, `running`, `succeeded`, `failed`, `cancelled`. `GET /api/v1/runs/{uuid}/events` — SSE; при повторном подключении передать `Last-Event-ID`. Polling `GET /runs/{uuid}` — резерв. Событие `queued` пока не записывается; поток начинается с `running`.
5. Только после `succeeded` получить `GET /api/v1/runs/{uuid}/results`. До этого `404 completed result not found`. `POST /api/v1/runs/{uuid}/cancel` возвращает `200` либо `409`, когда отмена уже невозможна.

`succeeded` означает, что вычислительный вызов завершился и результат сохранён. **Всегда проверять `result.optimization.status`:**

| Статус оптимизации | Представление |
|---|---|
| `optimal` | План на переданной области поиска; показывать `objective`, инвестиции, энергоаудит, качество данных |
| `feasible` | Допустимый план с остановкой по лимиту; показывать `gap` при наличии, не обещать оптимум |
| `infeasible` | Отдельное состояние «Ограничения несовместимы», `diagnostic`, без этапов строительства и метки успеха |
| `error` | Технический сбой расчёта; Run обычно `failed`, показывать `error_code`/`error_detail` и возможность повтора |

Нулевой `selected` при `optimal`/`feasible` может быть **правильным** решением оператора: строить нерентабельно при заданных условиях. Это не ошибка и не пустая загрузка.

## Что выводить из PlanResult

`optimization.selected[]` — `{site_id, option_id, year}`. `grid_upgrades[]` — `{grid_node_id, year, commissioned_year}`: `year` — год расхода бюджета, `commissioned_year` — первый год доступности дополнительной мощности. В `scenario.spec.grid_nodes[].upgrade_lead_years` указан срок ввода (по умолчанию 0). На временной шкале не включать усиление до `commissioned_year`. `battery[]`, `solar[]` — отдельные инвестиции. Идентификаторы сопоставлять с `scenario.spec`; названия и координаты брать из сохранённого снимка, не из встроенного демо.

`optimization.served_kwh`, `unmet_kwh`, `cashflow_rub` индексируются **ID сценария неопределённости**. Для `risk = expected_cvar` показывать `risk_metrics.cvar_alpha` и либо `cvar_loss_rub` (оператор), либо `cvar_unmet_kwh` (город). Вероятности должны быть заданы во входе и суммироваться до 1; UI не должен сам назначать вероятности.

`optimization.investment_rub_by_year[]` — год и CAPEX. `energy_audit[]` — по одной строке на площадку × год × сценарий: `served_kwh`, `grid_kwh`, `pv_used_kwh`, `pv_available_kwh`, `battery_charge_kwh`, `battery_discharge_kwh`, пиковые мощности и SoC на границах суток. `optimization.verification.passed` обязан быть `true` для допустимого плана; рядом доступны максимальные отклонения баланса, SoC, бюджета, сетевого узла и станции. Аудит ограничен 2000 строками: при `energy_audit_truncated = true` показывать, что подробные строки неполны. Это проверка ограничений модели, не AC power-flow.

`simulation[]` различается по `year`, `scenario_id`, `seed`. Отображать распределение по seed, а не выбирать один удачный запуск. `arrivals = served_sessions + refused_sessions`; `partial_energy_kwh` — уже отпущенная энергия в сессиях, не законченных до горизонта суток, она входит в `energy_kwh`, хотя сессия считается отказом. Это синтетическая событийная проверка очередей; диспетчеризация PV/накопителя в ней пока отсутствует. `explanations[]` — контрфактический пересчёт без выбранной площадки, а не причинность в наблюдаемых данных.

## Карта и отдельные модели

- `GET /api/v1/datasets`: история импортированных версий геоданных с `checksum`, `license`, `captured_at` (если известна) и `created_at`. Повторный импорт тех же байтов с теми же именем, источником, типом, лицензией и временем наблюдения возвращает прежнюю версию; старые точные дубликаты в истории сохраняются, но карта их не дублирует. `GET /api/v1/map?bbox=west,south,east,north&type=...`: GeoJSON, максимум 1000 объектов за запрос. `GET /api/v1/tiles/{z}/{x}/{y}?type=...`: MVT из PostGIS, кэш Redis с TTL 30 секунд и чтение из БД при отказе Redis. Разные версии с изменённым содержимым или происхождением пока могут сосуществовать на карте; селектор конкретной версии ещё не предусмотрен. Эти геослои **не связываются автоматически** с `PlanningInput`: при сопоставлении объектов показывать происхождение каждого слоя и не переносить численные значения молча.
- `POST /api/v1/corridors/check`: отдельная модель достижимости с отказом каждой станции; вход `CorridorSpec`, ответ `reachable`, `stops`, `legs`, `station_failure_impacts`, `assumptions`. Позиции станций должны уже соответствовать дорожному маршруту.
- `POST /api/v1/fleets/schedule`: отдельная MILP-модель парка; вход `FleetSpec`, ответ `status`, `schedule`, `peak_kw`, `trip_ids_served`, `end_energy_kwh`, `assumptions`. GTFS преобразуется **бэкенд CLI-адаптером** с отдельными назначениями машин, энергией рейсов и окнами зарядки. Не принимать GTFS-файл за готовый `FleetSpec` в браузере.

## Конкретные задачи фронтенда

1. Генерировать типы из `openapi.json` в CI и убрать ручные частичные типы для `PlanResult`/`ScenarioSpec`, сохранив runtime-проверку внешнего ответа. Схема результата должна обрабатывать `null`, пустые массивы, `infeasible` и `feasible`.
2. Разнести состояния задачи и оптимизации, вывести `diagnostic`, `gap`, `verification`, годы CAPEX и энергоаудит. Никакого общего «успеха» по одному лишь `Run.state`.
3. Сделать полноценный редактор допущений и происхождения с единицами, источником, датой наблюдения и валидацией диапазонов до отправки. Отмечать синтетический и наблюдаемый ввод по каждому объекту.
4. Для сравнения сценариев использовать одинаковые входные снимки, бюджеты и seed; показывать, какой показатель основан на MILP, какой — на SimPy, и какая часть ещё не подтверждена инженерно.
5. Добавить UI коридора и парка только на реальные контракты выше; состояние «нет назначений/энергии/техусловий» должно быть явным, без подстановки демо.
6. Покрыть E2E сценарии `feasible`, `infeasible`, пустого экономического плана, ошибок `422/503`, отмены и повторного подключения SSE. Пароль и API token не должны попадать в клиентский bundle или логи.

Сейчас фронтенд умеет загрузить полный пользовательский JSON и выполнить основной расчёт, но перечисленные специализированные представления и полный аудит ещё не реализованы. Бэкенд-развитие не следует имитировать статическими карточками: каждый показатель должен ссылаться на конкретное поле результата и входной снимок.
