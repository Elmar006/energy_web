# Дорожная карта бэкенда и доказательства корректности

Цель — выдавать проверяемые решения для **конкретной территории и подтверждённых входов**. Набор данных с реальными координатами, но придуманными спросом или резервом сети, не становится реальным кейсом. Прогноз будущего неизбежно содержит предположения: каждое такое поле должно быть помечено, диапазон неопределённости — показан, а рекомендация — проверена при изменении предположений.

## Как работаем

1. Для каждой возможности формулируем физические инварианты, единицы, источник данных и ожидаемый отказ при неполных сведениях.
2. Сначала делаем маленькие задачи с известным оптимумом или аналитическим ответом, затем сравнение с независимой симуляцией, затем сквозной запуск через Go API и PostgreSQL.
3. Для вычислительной модели сохраняем входной хеш, версии, seed, статус и область поиска. `optimal` означает оптимум **только для переданных кандидатов и выбранной дискретизации**.
4. Результат не получает статус инженерной проверки сети без схемы, нагрузок и AC power-flow; не получает статус прогноза реального спроса без валидации на независимой истории.
5. Исправление найденной ошибки сопровождается воспроизводимым контрпримером в тесте. Проверка небольшого примера не заменяет испытания масштаба и реальных наборов.

## Приоритеты

| Приоритет | Следующий результат | Проверка завершения |
|---|---|---|
| P0 | Строгий контракт входов: конечные значения, единицы, часовой пояс, различие `observed`/`derived`/`assumed`, полный манифест версий | Некорректные и неполные данные отклоняются до сохранения задачи; одинаковый снимок даёт одинаковый хеш и расчёт |
| P0 | Физический аудит оптимизатора: равенство баланса, ограничения узла/подключения/оборудования/накопителя, инвестиции по годам | Контрпримеры с нулевой сетью, PV, потерями накопителя и общим узлом; независимый пересчёт не находит нарушений |
| P0 | Реальные источники без скрытой подстановки: дорожный граф, сессии, резерв сети, GTFS и назначения парка; единый pipeline версионирования | Для каждого входного поля видны источник, время, лицензия и преобразование; отсутствие источника блокирует статус `observed` |
| P1 | Эксплуатационная проверка: очереди, отказы, реальные окна, диспетчеризация PV/накопителя, обратная связь с MILP | На отдельных сценариях симуляция подтверждает или отвергает ограничения качества; неподтверждённый план не маскируется статусом `optimal` |
| P1 | Альтернативы и многолетняя экономика: покрытие–CAPEX–NPV–риск, робастность и CVaR | Недоминируемые планы пересчитываются на одинаковых данных; CAPEX/NPV сверяются по денежным потокам, сценарии не раскрывают будущее инвестициям |
| P1 | Модель электробусов: GTFS-инстансы, перегоны, SoC, мощность и зарядная кривая | Каждый обеспеченный рейс имеет допустимую машину, энергию до выезда, время и место зарядки; конфликт получает конкретную причину |
| P1 | Надёжный вычислительный контур и RBAC | Потеря worker, отмена, повтор и Redis-outage не теряют задачу; доступ между проектами изолирован на уровне API и БД |
| P2 | Калибровка спроса и переносимость | Историческое разбиение без утечки, сравнение с сезонным baseline, проверка другой территории; при провале ML не допускается к расчётам |
| P2 | Схема сети и AC power-flow | Напряжения и загрузка линий проверены на подтверждённой схеме; уровень сетевой проверки отражён в результате |
| P2 | Бенчмарки и масштабирование | Полный перебор на малых задачах, общие seed для сравнения методов, профили CPU/памяти на нескольких размерах, пределы применимости опубликованы |

## Ближайшая последовательность реализации

1. Завершить независимый контроль физической допустимости с почасовыми рядами, SoC, CVaR и бюджетом; добавить намеренно противоречивые тестовые случаи. Уже сделан первый шаг: явное использование PV, баланс равенством и агрегированный энергетический аудит.
2. Связать импортированные источники с неизменяемым `PlanningInput`, отказавшись от ручного переноса чисел и идентификаторов. Проверять покрытие дат, зон, узлов и маршрутов; неизвестные значения не заменять нулём.
3. Ввести исполнение и проверку планов на последовательных временных отрезках, включая PV/накопитель, очереди и отказы. При несоответствии возвращать нарушение и пересчитывать в ограниченном вычислительном бюджете.
4. Реализовать эффективные альтернативы через ограничения покрытия и бюджета, с одинаковым расчётом метрик и явным статусом оптимальности/упрощений.
5. После предметной проверки — права доступа, контроль ресурсов, большие артефакты, наблюдаемость, аварийное восстановление и внешние интеграции.

## Текущая граница доказательства

Автоматические тесты доказывают согласованность реализованных моделей на заданных входах. Они **не доказывают**, что синтетический пилот описывает реальный город. Для прикладного решения нужны исторические сессии и/или обследование спроса, подтверждённые условия присоединения, цены, выбранный дорожный граф, реальные активы и полевые проверки. Если они отсутствуют, результат допустимо использовать как сценарный анализ с явно указанной неопределённостью.
