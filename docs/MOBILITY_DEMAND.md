# Потенциальный спрос из поездок и стоянок

`POST /api/v1/scenarios/from-mobility/preview` преобразует явные маршруты машин (`mobility-v1`) и существующий `PlanningInput` в новый расчётный сценарий. Это **предварительный расчёт без сохранения**: результат содержит `spec`, отдельные запросы на публичную зарядку `requests[]`, дневные срезы `calendar_profiles[]`, проверку энергии `audit` и SHA-256 нормализованного входа. Чтобы запустить оптимизатор, сохраните `spec` через `POST /api/v1/scenarios`, затем запустите полученный ID обычным `POST /api/v1/scenarios/{id}/runs`.

Этот путь отвечает на другой вопрос, чем импорт завершённых сессий. Сессии показывают уже отпущенную энергию; маршрут может породить **потребность в публичной зарядке даже там, где станции пока нет**. Расчёт не узнаёт реальные поездки автоматически: маршруты, расход, домашний доступ и вес машины поступают от пользователя и требуют своего источника или маркировки как допущения.

## Вход

Тело содержит два объекта: `input` — полный валидный `PlanningInput`; `mobility` — следующие данные. Идентификаторы зон должны существовать в `input.zones`. Часовой пояс IANA должен совпадать с `input.time_zone`, если тот уже задан. Даты `covered_dates` перечисляются по порядку без повторов и **заявляют полное покрытие** выбранных локальных дней, включая дни без заявок. Движок не может независимо проверить полноту выгрузки.

```json
{
  "schema_version": "mobility-v1",
  "time_zone": "Europe/Moscow",
  "covered_dates": ["2027-05-03"],
  "replace_zone_ids": ["taxi"],
  "source": "пример предполагаемой смены, не наблюдение оператора",
  "source_kind": "assumed",
  "vehicles": [
    {
      "id": "taxi-1",
      "segment": "taxi",
      "initial_zone_id": "taxi",
      "battery_kwh": 40,
      "initial_kwh": 10,
      "reserve_kwh": 2,
      "consumption_kwh_per_km": 0.2,
      "max_charge_kw": 22,
      "charging_efficiency": 0.9,
      "population_weight": 1,
      "activities": [
        {
          "kind": "park",
          "start_at": "2027-05-03T08:00:00+03:00",
          "end_at": "2027-05-03T09:00:00+03:00",
          "zone_id": "taxi",
          "private_charger_kw": 0,
          "public_allowed": true
        },
        {
          "kind": "drive",
          "start_at": "2027-05-03T09:00:00+03:00",
          "end_at": "2027-05-03T10:00:00+03:00",
          "destination_zone_id": "taxi",
          "distance_km": 60
        }
      ]
    }
  ]
}
```

Для быстрого запроса можно взять **синтетический** [`examples/demo.json`](../examples/demo.json) как `input`, а JSON выше как `mobility`. В PowerShell сохраните JSON выше в `mobility.json` и выполните из корня репозитория:

```powershell
$body = @{
  input = Get-Content .\examples\demo.json -Raw | ConvertFrom-Json
  mobility = Get-Content .\mobility.json -Raw | ConvertFrom-Json
} | ConvertTo-Json -Depth 100
$preview = Invoke-RestMethod -Method Post -Uri http://localhost:58080/api/v1/scenarios/from-mobility/preview -Headers @{ Authorization = "Bearer $env:API_TOKEN" } -ContentType application/json -Body $body
$preview.audit
```

В этом примере до поездки не хватает `4` кВт·ч в батарее. При КПД `0.9` предварительная заявка требует `4 / 0.9 ≈ 4.44` кВт·ч от поста. Она не означает, что существующая или предлагаемая сеть сможет её обслужить.

## Правила преобразования и проверки

| Поле | Смысл |
|---|---|
| `population_weight`, `population_weight_basis` | Сколько машин представляет маршрут при построении суммарного спроса. Для веса, отличного от 1, требуется текстовое основание; расчёт не проверяет его статистическую корректность. В `audit.vehicles[]` сохраняются вес и взвешенная публичная энергия. |
| `battery_kwh`, `initial_kwh`, `reserve_kwh` | Энергия батареи в кВт·ч и минимальный остаток после поездки. |
| `consumption_kwh_per_km`, `consumption_multiplier` | Удельный расход и множитель конкретной поездки; температура/сезон автоматически не измеряются. |
| `max_average_speed_kmh` | Объявленный верхний предел средней скорости (по умолчанию 250 км/ч, максимум 300). Он отбрасывает физически неправдоподобные пары расстояние/время, но не заменяет дорожную матрицу. |
| `private_charger_kw`, `public_allowed` | Доступ при стоянке. Если частная зарядка целиком покрывает дефицит до следующей поездки, заявка на публичную не создаётся. Иначе при разрешённом доступе весь дефицит становится публичной заявкой; совместного частичного покрытия пока нет. |
| `arrival_at`, `deadline_at`, `energy_from_charger_kwh` | Время стоянки и энергия заявки от поста. Времена обязаны содержать правильное UTC-смещение для указанного пояса; несуществующие моменты перехода на летнее время отклоняются. |

Маршрут чередует поездки и стоянки в хронологическом порядке. Проверяются зона и соответствие её `group` сегменту машины, доступное окно зарядки, максимальная мощность машины, невозможная поездка и баланс энергии. При отсутствии допустимого доступа API возвращает `422 invalid_mobility`, а не подставляет невыполненную зарядку как выполненную. При этом **публичная заявка условно удовлетворяется лишь внутри проекции следующей поездки**: фактическое обслуживание затем независимо оценивают размещение и симуляция.

`replace_zone_ids` заменяет `hourly_kwh[24]` только выбранных зон: это средняя потенциальная энергия публичной зарядки **на один объявленный локальный день**, с учётом весов машин. Для даты без заявок в знаменателе всё равно есть день. Не выбранные зоны, кандидаты, дороги, подключения, бюджеты и цены сохраняются из исходного `input`. У заменённых зон `arrival_profile` очищается, поскольку распределение уже выполненных сессий не является распределением новых потенциальных заявок. Суммы и происхождение доступны в `audit` и `spec.datasets[]`: манифест имеет `kind=derived` и отдельно сохраняет заявленный `source_kind=observed|assumed`. Хеш относится к нормализованному объекту `mobility`, а не к байтам исходного файла.

`calendar_profiles[]` возвращает локальную дату, тип рабочего/выходного дня, сезон, фактическую длительность суток с учётом смены UTC-смещения и 24 ячейки заявленного спроса по зоне. **Сейчас оптимизатор и SimPy используют усреднённый `hourly_kwh[24]`, а не эти разные дневные профили.** Профили предназначены для проверки входа и следующей версии календарной модели. Поэтому результат нельзя считать сезонным прогнозом, моделированием полного года или проверенной оценкой скрытого спроса города. Для надёжной оценки нужны репрезентативные маршруты и стоянки, доля домашних зарядок, независимые счётчики/сессии и отложенная проверка. `source_kind=observed` — заявление поставщика, не независимое удостоверение.

Размер HTTP-запроса ограничен 4 МиБ. Невалидный JSON даёт `400`, несогласованный маршрут — `422`, недоступный вычислитель — `503`; `502` означает, что внутренний сервис вернул некорректный расчётный снимок. Контракт и полные диапазоны полей есть в [OpenAPI](../openapi.json).

Ответ preview также содержит `source_canonical_json` — нормализованный JSON маршрутов, точные UTF-8 байты которого дают `source_sha256`. Если используется только preview и обычное сохранение `spec`, исходные маршруты автоматически не сохраняются; для воспроизведения их необходимо архивировать отдельно. Сохраняющий маршрут ниже решает эту проблему.

`compiler_source_sha256` фиксирует хеш исходников Python engine на момент преобразования, а `compiler_pydantic_version` — версию библиотеки разбора контракта. Эти сведения помогают обнаружить несовпадение вычислительной среды при повторе.

## Сохранение воспроизводимого источника

`POST /api/v1/scenarios/from-mobility` принимает тот же `input` и `mobility`, а также `name`. Он повторно валидирует результат Python, затем в одной транзакции сохраняет новый сценарий, версию набора, исходный `input` и нормализованные маршруты. В `scenario.spec.datasets[]` появляется UUID версии. Ответ содержит `scenario.id`, `dataset_version_id`, `source_sha256`, `base_sha256` и одноразово выданный `source_access_token`.

Сохраните `source_access_token` в защищённом хранилище: он **не восстанавливается** из БД. Для чтения `GET /api/v1/scenarios/{id}/mobility-origin` нужны обычный API bearer и заголовок `X-Mobility-Source-Token`. Ответ возвращает исходный сценарий, нормализованные маршруты и хеши; неверный capability даёт `404`. Ротация общего API-токена не меняет этот capability. Пока нет проектов и RBAC, поэтому это контроль доступа к конкретному источнику, а не полноценная изоляция команд. Маршруты с личными идентификаторами не следует загружать без согласованной политики хранения и доступа.

Повтор одного и того же `POST` пока создаёт новую версию сценария; сохраняющий маршрут не идемпотентен. Оптимизация запускается отдельно через `POST /api/v1/scenarios/{id}/runs`.

В результатах запуска `metadata.input_quality.demand_scope=mobility_potential` появляется, если все зоны получены из маршрутов. Поля `mobility_derived_zone_ids` и `mobility_sources` показывают затронутые зоны, хеши и заявленный тип исходных записей. При смешанном происхождении спроса `demand_scope=mixed`.

Начало и конец каждой поездки и стоянки должны лежать в объявленных `covered_dates`; ночь через границу суток требует включить обе даты. Отсутствующие дни или неполные траектории нельзя молча выдавать за нулевой спрос.

В `calendar_profiles[].zone_hourly_kwh` хранятся только зоны с ненулевыми заявками за этот день; отсутствие зоны означает нулевые заявки для неё. Все объявленные даты остаются в массиве, включая дни без заявок. Такое разреженное представление не создаёт массив `дни × все зоны × 24` для большой территории.
