# Воспроизводимый эксперимент: размещение и эксплуатация

**Энергоконтур · задача № 03 · техническое доказательство.** Последний повтор: 1 октября 2026 года. Основной результат: обслуженная энергия и очередь улучшаются при более высоком CAPEX. Это сценарное сравнение, а не экономическая валидация города.

## Методика сравнения

Проверяются `existing`, `density` и `optimized`. Первый сохраняет существующий сценарный актив; второй добавляет допустимые комплекты по плотности; третий решает городской MILP. У всех один расчётный вход, ежегодные пределы 7 и 3 млн ₽ и общий предел 10 млн ₽. **Одинаковый предел бюджета не означает одинаковый фактический CAPEX.**

Инвестиции рассчитываются для двух сценариев роста; основной эксплуатационный срез — базовый сценарий 2028 года. Каждая проверка использует три последовательных суток. Одинаковые внешние потоки прибытий применяются к сравниваемым планам, seed задаёт воспроизводимую случайность. Симулятор принимает инфраструктуру плана, но выбирает обслуживание собственной логикой.

Протокол и lock: [protocol_monaco.json](../evidence/production-2026-09-30/protocol_monaco.json), [SHA lock](../evidence/production-2026-09-30/protocol_monaco.lock.json). Итоговый набор — **20001–20030**; отделён от перечисленных development seed. Этот набор уже применялся 30 сентября: повтор 1 октября является регрессией без настройки, а не новым независимым испытанием. Протокол фиксирует сравнение `optimized_minus_density`, первичную метрику `service_fraction`, годы, бюджет, условия, seed и SHA движка.

Интервалы строятся парным непараметрическим bootstrap: 5000 resample, seed 20260924. Интервал разности предпочтительнее сравнения двух независимых полос, поскольку прибытия общие. Он описывает случайность модели при фиксированных предположениях и не измеряет ошибку прогноза реального спроса.

## Базовый результат, 2028 год

| Метрика | Существующая сеть | По плотности | MILP |
|---|---:|---:|---:|
| Обслуженная доля энергии | 33,04% | 93,29% | **98,57%** |
| Отпуск, кВт·ч/сутки | 534,34 | 1 514,40 | **1 600,73** |
| Среднее по seed p95 ожидания, мин | 38,50 | 27,64 | **14,77** |
| Отказанные сессии за трёхсуточный прогон, среднее | 83,97 | 10,00 | **2,33** |
| Новый CAPEX за горизонт, млн ₽ | 0 | **3,70** | 5,20 |
| NPV proxy за горизонт, млн ₽ | 7,88 | **17,54** | 17,03 |
| Отпуск / установленная энергия за сутки | **50,60%** | 30,34% | 23,48% |
| Доля спроса в дорожной достижимости | 50,63% | **100%** | **100%** |

Средняя парная разность обслуживания MILP − density: **+5,28 п.п.**, 95% интервал **[4,88; 5,67] п.п.** В JSON доли записаны в `[0,1]`; перевод в проценты выполнен только при представлении.

`nameplate_energy_utilization` — отпуск за сутки, делённый на установленную мощность × 24 ч. Это не занятость разъёмов, не загрузка подстанции и не отпуск относительно договорного предела. NPV proxy использует предположенные цены, наблюдение симулятора и годовую экстраполяцию; существующие капитальные вложения не включены в новый CAPEX. Его нельзя использовать как локальное финансовое заключение.

**Интерпретация:** больший комплект уменьшил очередь и увеличил обслуженную энергию. Географический охват двух новых планов одинаков; увеличение ресурса снижает относительную загрузку и стоит дороже. MILP не доминирует эвристику по всем показателям. Для доказательства меньших инфраструктурных издержек нужен отдельный эксперимент при одинаковом сервисе либо заранее определённая метрика жизненного цикла.

## Стресс-проверки и физическая допустимость

В JSON сохранены отключение станции, спрос ×0,75/×1,25 и сетевой резерв ×0,75/×1,25. При отказе выбранной для каждого плана наиболее нагруженной станции обслуженная доля составляет 0% для existing, 42,40% для density и 93,92% для optimized. **Отказывающий объект определяется внутри каждого плана**, поэтому это проверка его уязвимости, а не одинаковый внешний адрес отказа для всех вариантов.

Solver: `optimal`, gap 0 на заданном пространстве кандидатов и почасовой сетке. Проверка MILP сообщает отсутствие превышения бюджета, лимитов мощности, баланса энергии и SoC. Каждый прогон симулятора требует успешного энергетического аудита; при нарушении benchmark прерывается. Сохранены **630 строк** «план × год/условие × seed».

Формальная сервисная приёмка `accepted/rejected/inconclusive` в этом benchmark **не применяется**. Она запускается отдельно с `RunSpec.service_requirements`; отсутствие порогов не следует трактовать как `accepted`. Проверки лимита узла не включают AC power-flow.

## Воспроизведение

Повтор на закреплённом JSON не требует заново вызывать OSRM. Находясь в корне репозитория:

```sh
python -m pip install -r engine/requirements-dev.txt
cd engine
python -m energy.benchmark \
  --input ../examples/regression/monaco/commission_monaco.json \
  --protocol ../docs/evidence/production-2026-09-30/protocol_monaco.json \
  --protocol-lock ../docs/evidence/production-2026-09-30/protocol_monaco.lock.json \
  --output ../data/benchmark/monaco-rerun.json
```

В PowerShell замените переносы `\` на обратный апостроф или выполните последнюю команду одной строкой. Альтернатива — собранный образ `energy-engine` с монтированием корня репозитория, working directory `/workspace/engine` и теми же аргументами. Вывод направляйте в новый файл `data/benchmark/`; старые results/locks не переписывайте.

При изменении `.py`-исходников engine прежний протокол отклонит несовпадение SHA. Сначала задайте новый протокол и его lock **до запуска**, затем сохраните новый результат. Повторное использование уже известного seed-набора не превращает проверку в независимую предрегистрацию.

Для повторного получения географии используйте фиксированный PBF, проверьте SHA, запустите [build_input.py](../../examples/regression/monaco/build_input.py), подготовьте OSRM-граф по [документации дорожной матрицы](../ROUTING.md) и примените [routing.py](../../engine/energy/routing.py). Новая версия графа или дорожного профиля может изменить времена: это новый вход, а не тот же эксперимент.
