# Статус реализации

Эта страница описывает **код, который действительно запускается**. Архитектурные границы — в [ARCHITECTURE.md](ARCHITECTURE.md), незавершённые изменения с критериями приёмки — в [ROADMAP.md](ROADMAP.md). Запланированные возможности не входят в текущую реализацию.

## Работает сейчас

- `POST /api/v1/scenarios/from-mobility/preview` превращает явно переданные поездки, стоянки, батареи, домашний доступ и веса машин в **потенциальные** запросы на публичную зарядку и новый `PlanningInput`. Проверяются допустимость поездок, окна, пояс/DST и баланс энергии; возвращаются заявки, дневной календарь, аудит и SHA-256 нормализованного входа. В текущей поставке `spec` содержит `service_calendar` и `charging_requests`: оптимизатор и SimPy используют их датированные окна, а не только средний 24-часовой профиль. Иные зоны могут оставаться в явно отмеченном режиме типовых суток. Это параметрическая оценка из предоставленной мобильности без проверки репрезентативности реальных поездок. [Контракт и пример](MOBILITY_DEMAND.md), [датированный формат](DATED_DEMAND.md).
- `POST /api/v1/scenarios/from-mobility` сохраняет рассчитанный сценарий, версию набора, исходный расчётный вход и нормализованные маршруты в одной транзакции. В ответе одноразово выдаётся capability для `GET /api/v1/scenarios/{id}/mobility-origin`; чтение требует и bearer, и capability. Хеш исходника и отпечаток Python-кода/версии Pydantic хранятся для проверки повтора. Повторный POST пока создаёт новый сценарий; проекты/RBAC не реализованы. [Порядок работы](MOBILITY_DEMAND.md).
- `RunSpec` сохраняется вместе с задачей: явные seed (до 100), длительность симуляции, лимит решателя, набор альтернатив и число объяснений проходят API → PostgreSQL → worker → Python. `validation` требует минимум 30 seed; необязательные `service_requirements` задают пороги доли энергии/сессий, отказов и ожидания. Для основного и альтернативных планов возвращаются `accepted/rejected/inconclusive` по сценариям и годам с 95% интервалом **модельной случайности**; без порогов — `not_evaluated`. Worker сверяет, что принятый ответ связан с сохранёнными порогами и охватывает условия. Повтор с тем же ключом и отличающимися параметрами возвращает конфликт. Старые задачи после миграции получают пометку `legacy_inferred`; большие ответы свыше 16 МиБ пока отклоняются. [Контракт и границы](RUN_SPEC.md), [приёмка](SERVICE_ACCEPTANCE.md).

- Добавочный `run-spec-v2` разделяет `development_seeds` и итоговые `simulation_seeds`. При явных требованиях обслуживания он может до трёх раз пересчитать план с дополнительной площадкой по разработочным потокам, сохранить историю и только затем выполнить итоговую приёмку на непересекающихся seed. Это ограниченная эвристика; `accepted` означает выполнение заданных порогов в модельной симуляции, не доказанную оптимальность по очередям. Старые `run-spec-v1` и вызов без тела не меняются. [Схема запуска](RUN_SPEC.md).
- Датированный `ServiceCalendar` покрывает до 14 последовательных локальных дней, включая переходы IANA/DST. `ChargingRequest` задаёт окно, энергию, предел мощности автомобиля, исходный SoC, вес и происхождение. Оптимизатор распределяет энергию по допустимым часовым UTC-слотам после дорожного времени; SimPy использует реальные моменты прибытия и дедлайна. Старый 24-часовой профиль по-прежнему доступен по явно отмеченным зонам. Масштабирование короткого периода на год обозначается `assumed_repeat`, не выдаётся за измеренный год. [Формат и ограничения](DATED_DEMAND.md).
- `POST /api/v1/artifacts/demand` принимает не более 64 МиБ JSON с календарём и заявками, возвращает content-addressed манифест `sha256:<hex>`. Сценарий может хранить только `demand_dataset`, а API и worker сверяют хеш/размер и материализуют вход до передачи Python. Реализован локальный адаптер общего тома API/worker; S3, проектная изоляция артефактов и вынесение **крупных результатов** ещё не реализованы. [Протокол](DATED_DEMAND.md).

- Go API хранит неизменяемые сценарии, хеш входа, расчётные задачи, события и результаты в PostgreSQL/PostGIS. Worker арендует задачи, продлевает lease и публикует результат по attempt ID; отменённая или устаревшая попытка не перезаписывает актуальную. Таймаут worker учитывает заявленный лимит решателя и до трёх повторных расчётов объяснений, вместо фиксированных 15 минут.
- Сценарные и расчётные use case вынесены из HTTP handlers в `internal/planning`: валидация, чтение, запуск и отмена отделены интерфейсами от SQL-адаптера. Хеш сценария соответствует сохранённому JSONB-снимку; миграция исправляет хеши старых записей. Миграции SQL применяет одноразовый Go-процесс на новой и существующей БД с advisory lock и проверкой SHA-256. Запросы по UUID используют типизированный ключ; списки и очередь имеют отдельные индексы и детерминированный порядок. [Документ для фронтендера](frontend/BACKEND_HANDOFF.md) фиксирует фактические API и состояния.
- Python/HiGHS решает многопериодную задачу размещения для режима города или оператора с общими инвестициями для всех сценариев, годовыми бюджетами, мощностью оборудования, договорным пределом станции, резервом узла, усилением сети, накопителем и PV. Усиление узла доступно после заданного срока ввода: CAPEX учитывается в год инвестиций, результат сообщает год ввода; симуляция использует тот же срок. В городском режиме при одинаковом покрытии предпочтение отдаётся меньшему времени поездки, затем экономике. При обоснованных вероятностях работает ожидаемый результат с явным CVaR-ограничением на убыток оператора или необслуженную энергию города; без вероятностей доступен худший сценарий. Результат содержит статус решателя, метрику CVaR и gap, если он доступен.
- Баланс станции теперь задаётся равенством с отдельным ограниченным использованием PV. Результат содержит инвестиции по годам и энергетический аудит по площадке, году и сценарию; после решения независимо пересчитываются отклонения баланса, перегрузки узла, подключения и оборудования, использование PV и перерасход бюджета. При значимом нарушении результат не публикуется как допустимый план. Контракт отклоняет нечисловые и бесконечные значения до построения модели.
- Расчёт возвращает дополнительные планы минимального CAPEX для уровней обслуживания 0%, 50% и 100% в каждом году и сценарии неопределённости. Они используют тот же MILP, бюджет, CVaR и входной снимок, отдельно проходят физический аудит и событийную симуляцию с теми же seed. Основной и альтернативные планы содержат спрос, обслуживание и дефицит по году и сценарию. Статус каждого уровня сохраняется; сетка уровней пока не является полным доказанным фронтом Парето.
- SimPy моделирует прибытия и очереди: при наличии `arrival_profile` использует наблюдённые часы начала и эмпирические квантили энергии сессий; без него остаётся явно параметрический поток. `parameters.simulation_days` задаёт непрерывный горизонт 1–14 суток (по умолчанию 3): сессии, очередь и SoC накопителя переходят через полночь; только последний незавершённый день обрывает сессии. `day_dispatch[]` показывает дневной энергобаланс и SoC на границах, `dispatch_verification` проверяет баланс накопителя за весь горизонт. `operational_validation` сопоставляет доли обслуживания с почасовым MILP по каждому году и сценарию, а энергетические объёмы нормирует на сутки; `operational_economics` нормирует отпуск и закупку перед годовой экстраполяцией NPV. Разрывы видны, а не скрываются статусом `optimal`. Минутная диспетчеризация соблюдает общий узел, договорный предел станции, PV и накопитель. Для датированных зон поток использует явные прибытия и дедлайны; для старых профильных зон сохраняется повтор типовых суток. Отдельный контрфактический пересчёт показывает влияние удаления выбранной площадки.
- Отдельный расчёт коридора проверяет маршрутный запас энергии, сезонный множитель и отказ любой станции. Отдельная MILP-модель парка назначает зарядку по слотам, учитывая рейсы, SoC, число постов и общий лимит мощности.
- CLI-адаптер GTFS читает календарь обслуживания и времена назначенных рейсов из ZIP, а назначение автобусов, энергию рейсов и окна зарядки требует отдельным операционным JSON. Он консервативно округляет интервалы до расчётных слотов, проверяет наложения, сохраняет SHA-256 обоих источников и выдаёт `FleetInput` вместе с манифестом происхождения.
- GeoJSON FeatureCollection импортируется транзакционно с проверкой координат и происхождения. Повторный импорт идентичных байтов при том же имени/источнике/типе/лицензии/времени наблюдения идемпотентен, включая конкурирующие вызовы; карта скрывает старые точные дубликаты, не удаляя их из аудита. Ответ списка версий содержит время наблюдения и импорта. GeoJSON и векторные тайлы выдаются из PostGIS через географический use case. Он проверяет границы запросов и координаты тайла до репозитория; Redis кеширует тайлы 30 секунд, а при его отказе ответ берётся из PostgreSQL. PostgreSQL остаётся источником задач и результатов.
- Через `POST /api/v1/datasets/import` GeoJSON теперь можно загрузить из API. Из четырёх **явно выбранных UUID версий** зон спроса, площадок, узлов и дорожных связей сервис собирает `PlanningInput`, проверяет наборы и часовой пояс, показывает preview с отчётом качества и затем сохраняет неизменяемый сценарий. Неизвестные `hourly_kwh`, `headroom_kw` или `minutes` не подменяются нулём. Точные UUID, SHA-256 и источник попадают в манифест, а оборудование, бюджет, тарифы и сценарии неопределённости помечаются как неподтверждённые предположения. [Формат и ограничения](DATASET_SCENARIOS.md).
- Адаптер зарядных сессий CSV строит 24-часовой профиль отпущенной энергии, **отдельный профиль начала сессий**, выборочную межсуточную дисперсию количества прибытий, 101 эмпирическую квантиль энергии и фактический средний объём сессии. Он проверяет сохранение энергии между этими рядами. Почасовая нагрузка распределяется равномерно по длительности сессии, поскольку сам CSV не содержит интервальных показаний счётчика; это **вычисленная оценка, не измеренный профиль мощности**. SHA-256 и источник записываются в манифест; зоны без наблюдений не заполняются нулями. Пропущенный день по любой зоне отклоняется: считать его нулевым можно только при явном `coverage_complete=true`, то есть заявлении поставщика о полном покрытии выгрузки. `days_with_sessions` и сама заявка сохраняются в профиле и отчёте качества. По умолчанию CSV помечен как предположение, `observed` указывается только явно. Границы интерпретации подробно разобраны в [расчёте на реальных данных](REAL_DATA_CALCULATION.md).
- Go API принимает CSV выполненных зарядных сессий и почасового резерва сети напрямую через multipart-загрузку к выбранному сценарию. Python применяет те же проверенные адаптеры, Go повторно проверяет новый снимок и атомарно сохраняет исходные байты, SHA-256, UUID версии и новый неизменяемый сценарий. Идентичные повторные и одновременные загрузки возвращают прежнюю версию. Исходный CSV можно скачать по защищённому API; расчёт worker запускается по ID нового сценария. [Команды и контракты](DIRECT_UPLOAD.md). Фронтенд-форма для этих CSV пока не написана.
- CLI-адаптер сетевого резерва принимает полный почасовой CSV для каждого узла, отклоняет неизвестные узлы, пропуски, дубли и отрицательные значения, записывает источник и хеш. При тестировании синтетического CSV его можно пометить `assumed`; метка `observed` остается заявлением поставщика, не независимым подтверждением.
- CLI-адаптер OSRM строит матрицу достижимости и времени поездки на основе выбранного пользователем автомобильного OSM-графа. Проверяются недостижимые пары, лимит времени и удалённость координат от дорожного графа; происхождение графа и хеш ответов добавляются в манифест. В Compose есть необязательный профиль `routing`, требующий заранее подготовленного графа.
- Если дорожный граф не связывает зону с площадками, её энергия остаётся необслуженной без ложного объявления всего расчёта невозможным; при обязательном минимуме покрытия возвращается причина несовместимости. Пустой план допустим в режиме оператора и явно показывается в интерфейсе.
- Next.js предоставляет локальный интерфейс со сценарием, картой 2ГИС MapGL при наличии ключа `DGIS_MAPGL_API_KEY`, расчётом, альтернативами, происхождением входов, энергетическим аудитом, посуточной симуляцией, этапами и объяснениями. Можно задать собственный ID стиля через `DGIS_MAP_STYLE_ID`. Пользователь может загрузить собственный `PlanningInput` JSON: Python проверяет контракт до сохранения, PostgreSQL хранит неизменяемый снимок, интерфейс открывает его повторно и использует его площадки, зоны и годы. Без ключа карты нет, но расчёты работают. Загрузка картографических тайлов с действующим ключом пока не проверена. Весь встроенный демонстрационный спрос и энергетические данные являются предположениями.
- Для одного закреплённого смешанного OSM/сценарного кейса реализован воспроизводимый benchmark: существующая сеть, эвристика плотности и MILP на одинаковом входе, 30 парных seed, отказ станции, рост спроса, физический аудит и bootstrap-интервалы. Новый прогон на seed 10001–10030 использует проверяемый протокол, который фиксирует вход, хеш вычислительных исходников, бюджет, методы, условия и первичную метрику до запуска; [числа и границы вывода](commission/REPORT.md). Это пока не бенчмарк на подтверждённой истории оператора или целевой российской территории.
- OpenAPI 3.1 генерируется в [openapi.json](../openapi.json) из схемы расчётного входа и публичных маршрутов.

## Пока не реализовано

- Автоматическое скачивание, версионирование и регулярное обновление OSM-экстрактов; H3-иерархия и масштабируемый кэш дорожных матриц. OSRM сейчас вызывается отдельным воспроизводимым CLI-шагом.
- Явный выбор версии геоданных в карте и управление заменой изменившихся слоёв: сейчас точные дубликаты подавляются, но разные версии одного источника могут сосуществовать.
- Автоматический выбор подходящих версий и сопоставление произвольных OSM/муниципальных полей с предметной схемой. Сборка теперь работает для четырёх **нормализованных** GeoJSON-слоёв; произвольный OSM-экстракт необходимо явно преобразовать. Дорожное время в загруженном слое не сверяется с геометрией; для воспроизводимой матрицы нужен выбранный граф OSRM.
- Автоматическое получение GTFS, подтверждение назначений машин и расхода энергии у оператора, зарядные кривые и перегоны; импортёр требует назначения и окна как отдельный вход, не выводит их из расписания.
- Прогнозирование CatBoost, калибровка спроса на наблюдениях, статистическая проверка переноса модели на другой город.
- Калиброванная и независимая оценка городского латентного спроса. Новый `mobility-v1` строит потенциальные заявки из **переданных** маршрутов и допущений, но репрезентативность выборки, долю домашнего доступа и скрытые поездки не оценивает. CSV-адаптер по-прежнему выводит только уже состоявшиеся сессии; `metadata.input_quality` отмечает эту границу и недостаточный объём истории.
- Автоматическая сверка пользовательского происхождения данных с первоисточником, полная полевая provenance-модель, сезонные/многолетние реальные профили сетевого резерва и официальный процесс проверки условий присоединения.
- Полная электрическая схема и AC power-flow в pandapower. Проверяются лимиты подключения и узла, но результат не является заключением о режиме сети.
- Адаптивные решения после наблюдения сценария, полный доказанный фронт недоминируемых альтернатив и расширенные бенчмарки на подтверждённых данных/нескольких территориях. Один модельный baseline-бенчмарк теперь есть, но его нельзя выдавать за внешнюю валидацию. Текущий CVaR действует только на заданное дискретное распределение сценариев; вероятности ещё не оцениваются из исторических данных.
- Полный подтверждённый сезонный год, долгосрочная деградация накопителя, 15-минутная инвестиционная модель и полноценный цикл генерации ограничений по результатам симуляции. Датированные заявки уже работают на коротком горизонте, но без репрезентативного года и независимой истории не доказывают сезонную устойчивость. `run-spec-v2` пробует до трёх дополнительных закреплённых площадок; он не является общим алгоритмом исправления всех нарушений сервиса.
- Полные почасовые ряды и внешнее хранение крупных аудитов; текущий ответ включает агрегаты площадок и ограничен 2000 строками с явным флагом усечения.
- Многопользовательские проекты/RBAC, внешнее S3-хранилище, производственный провайдер аутентификации, отчёты PDF и отказоустойчивые контрольные точки решателя. Пока миграция использует тот же логин БД, что API/worker; отдельная роль владельца схемы ещё не выделена.

## Границы интерпретации

NPV в текущем ядре вычисляется из заданных тарифов/затрат и экстраполяции короткого периода: старый 24-часовой профиль масштабируется на год, а календарь заявок использует явный `annualization_factor` с основанием `assumed_repeat`. Это сценарная экономика, не инвестиционное заключение. Годы должны быть последовательными. Синтетический пилот на координатах Екатеринбурга не подтверждает фактический спрос или доступную сетевую мощность города. Результат `optimal` относится только к переданному набору кандидатов и временной дискретизации.

Текущая аутентификация фронтенда — общий демонстрационный пароль. Она подходит для локального пилота, но **не** реализует проектные роли и разграничение пользователей. Все вошедшие видят сохранённые сценарии; не загружайте конфиденциальные реальные наборы в многопользовательское окружение до реализации RBAC. Публичный Go API использует статический bearer token; перед внешней эксплуатацией потребуются полноценная аутентификация, авторизация и TLS. Пометка `observed` в пользовательском JSON пока не подтверждается независимой сверкой с источником.
