# Развёртывание и границы эксплуатационной готовности

**Проверено: 30 сентября 2026 года. Область: закрытое окружение одной организации.**

Система не создаёт зарядные площадки, сетевые узлы, спрос и тарифы при открытии страницы. Новый экземпляр начинает с пустой БД. Пользователь выбирает сохранённую версию или загружает вход. Тестовые наборы в `examples/` импортируются только явно; их успешный расчёт не подтверждает реальные условия территории.

## Две конфигурации

| Конфигурация | Назначение | Доступ |
|---|---|---|
| `compose.yaml` + `.env` | Разработка и локальные проверки | Порты привязаны к loopback; API и БД доступны локальным инструментам |
| `compose.production.yaml` + `.env.production` | Закрытое развёртывание одной организации | Только frontend на loopback; PostgreSQL, Redis, Go и Python во внутренней сети |

Production-файл самостоятельный. **Не объединяйте его с `compose.yaml`**: публикация портов из development-конфигурации нарушит изоляцию. Имя проекта задавайте постоянно: оно определяет Docker volumes. Другой project name создаст другое хранилище.

## Подготовка

1. Скопируйте `.env.production.example` в `.env.production`. Ограничьте доступ к файлу средствами ОС и храните его вне Git.
2. Сгенерируйте **пять разных** секретов: `POSTGRES_PASSWORD`, `RUNTIME_DB_PASSWORD`, `API_TOKEN`, `SESSION_SECRET`, `APP_ACCESS_PASSWORD`. Подходящий генератор: `python -c "import secrets; print(secrets.token_hex(32))"`. Запустите отдельно для каждого значения. Пароли БД должны содержать URL-safe символы.
3. Задайте `APP_PUBLIC_ORIGIN`, например `https://planner.company.ru`, без завершающего `/`, пути и query. Настройте соответствующий HTTPS reverse proxy и ограничьте доступ доверенной сетью/VPN. HTTPS, сертификаты и внешняя аутентификация не создаются Compose-файлом.
4. При необходимости укажите браузерный ключ 2ГИС `DGIS_MAPGL_API_KEY` и ограничения его доменов у поставщика. Это публичный браузерный ключ; серверный `API_TOKEN` клиенту не передаётся.

```bash
python scripts/production_preflight.py --env-file .env.production
docker compose --env-file .env.production -f compose.production.yaml -p energy-production config --quiet
docker compose --env-file .env.production -f compose.production.yaml -p energy-production up -d --build
docker compose --env-file .env.production -f compose.production.yaml -p energy-production ps --all
```

Не публикуйте вывод полного `docker compose config` или `docker inspect`: в них содержатся секреты. Preflight выводит только имена ошибочных параметров. После запуска проверьте реальный HTTPS-вход, `Secure` cookie и доступ только через доверенный ingress. Эти внешние проверки обязательны на целевом сервере.

Compose использует переменные shell раньше значений `--env-file`. Preflight учитывает такое переопределение, включая пустые значения. Не оставляйте development-секреты экспортированными при запуске production; проверьте конфигурацию в той же shell, из которой запускаете Compose.

## Учётные данные и права

`migrate` получает владельца `energy_owner`, применяет контрольные суммы миграций и завершается. `runtime-role` создаёт/обновляет отдельный логин `energy_runtime`, выдаёт необходимые CRUD-права и завершается. API и worker получают только этот логин. Владелец не используется для обслуживания HTTP-запросов.

API/worker при старте отклоняют суперпользователя, владельца таблиц, роль с CREATE в `public`, административными правами или членством в других ролях. `APP_ENV` обязателен. После каждой новой миграции выполните `migrate`, затем `runtime-role`: новые таблицы не получают автоматических широких default grants. Конфликт привилегий приводит к отказу запуска; не обходите проверку сменой `APP_ENV`.

Production BFF требует `APP_AUTH_MODE=private-single-tenant`, независимый `SESSION_SECRET`, сильные секреты, HTTPS origin и `APP_COOKIE_SECURE=true`. Сессия имеет проверяемый HMAC, срок 12 часов, `HttpOnly`, `SameSite=Strict`, `Secure`. Изменяющие запросы `/api/*` требуют точный настроенный Origin; произвольные `X-Forwarded-*` не расширяют разрешение.

Общий пароль даёт полный доступ ко всем сценариям этого экземпляра. **Это не RBAC и не изоляция команд.** Отдельные организации должны иметь отдельные экземпляры/хранилища либо ждать реализации пользователей, проектов и проверок принадлежности каждого объекта.

## Защита ресурсов

Ограничены объём тела JSON/upload, время ожидания HTTP, память/PID контейнеров, CPU вычислителя и объём Docker-логов. API/worker/Python работают без root и без Linux capabilities; их root filesystem read-only. Python имеет ограниченный tmpfs. Redis ограничен по памяти и остаётся ускорителем: очередь и результаты долговечны в PostgreSQL.

Есть локальный лимит входа 10 попыток в минуту на процесс. При нескольких экземплярах нужен общий лимит на ingress. Настройте ограничения одновременных загрузок и запусков, мониторинг диска, PostgreSQL, очереди и контейнеров. Контейнерный лимит памяти **не равен** отдельному лимиту процесса каждой задачи. Отмена задачи пока не гарантирует немедленного завершения решателя Python; вычислительная изоляция отдельного запуска остаётся блокером публичной эксплуатации.

## Резервное копирование

Сохраняются **вместе** PostgreSQL и volume артефактов. Спрос хранится по адресу `<sha-prefix>/<sha256>.json`; потеря этих файлов делает связанные снимки невоспроизводимыми. Redis восстанавливать из backup не требуется.

Скрипт `scripts/production_backup.py` принимает только существующий production-проект. Он не печатает секреты, проверяет остановку frontend/API/worker, создаёт новую директорию, пишет binary `pg_dump`, архив артефактов и манифест SHA-256 с числом миграций/сценариев/задач. Параллельные внешние записи в БД также должны быть остановлены.

```bash
docker compose --env-file .env.production -f compose.production.yaml -p energy-production stop frontend api worker
python scripts/production_backup.py --env-file .env.production --project energy-production backup --directory backups/2026-09-30
docker compose --env-file .env.production -f compose.production.yaml -p energy-production start api worker frontend
```

Если backup завершился ошибкой, сохраните логи в контролируемом месте, исправьте причину и создайте **новую** директорию. Возобновляйте приложения после завершения обслуживания. Скрипт не объявляет частичную копию успешной. Каталог backup может содержать конфиденциальные данные: шифруйте его и храните копию вне хоста. `backups/` исключён из Git. RPO задаётся расписанием и хранением копий, а RTO необходимо измерить на целевом объёме; показатели QA-стенда не являются SLA.

## Проверка восстановления

`recover-check` проверяет манифест и архив **до** записи. Он создаёт только новую БД с именем `energy_restore_*` и новый каталог; существующая БД не очищается. Проверяются восстановленные счётчики и SHA-256 каждого опубликованного артефакта. Архивы с выходом за каталог, ссылками и специальными файлами отклоняются.

```bash
python scripts/production_backup.py --env-file .env.production --project energy-production recover-check \
  --directory backups/2026-09-30 --database energy_restore_20260930 \
  --artifact-output data/recovery-20260930
```

Это проверка recovery, а не автоматическое переключение приложения. Для аварийного восстановления разворачивайте отдельный экземпляр с теми же версиями PostgreSQL/миграций, восстановите владельца/схему и соответствующие артефакты, запустите `runtime-role`, проверьте права файлов UID 65532 и хеши, выполните smoke, затем переключайте ingress. Не запускайте старые бинарники на более новой несовместимой схеме. Production-данные и volumes не удаляйте командами `down -v`.

## Обновление

Перед обновлением сохраните проверенный backup и зафиксируйте версии образов/commit. В окне обслуживания остановите приложения, примените миграции и runtime grants, затем запустите новую сборку. Сохранённые синтетические кейсы не удаляются автоматически: их надо отличать по названию, манифесту и `assumed`, а удаление — отдельное решение владельца данных.

В CI добавлены тесты конфигурации/backup и сканеры зависимостей. Зелёный локальный прогон не означает успешный удалённый CI или проверенный TLS-ingress. Исторические benchmark lock-файлы не переписываются: новый код получает отдельный протокол и результат.

## Незакрытые блокеры

| Приоритет | Блокер | Критерий закрытия |
|---|---|---|
| P0 для совместного доступа | Пользователи, проекты, RBAC; объектная авторизация и персональный аудит | Чужие наборы, артефакты, задачи, результаты и SSE недоступны во всех маршрутах; конкурентные integration-тесты |
| P0 для вычислительного сервиса | Отдельный процесс на задачу, принудительная отмена, CPU/RAM/time budget | Решатель завершается при отмене/таймауте; соседние задачи сохраняются; длительные расчёты парков проходят через очередь |
| P0 на целевой инфраструктуре | Реальные TLS/ingress, общие лимиты, наблюдаемость и off-host backup | Проверены внешний HTTPS-вход, alarm/recovery, конфиденциальность логов и секретов |
| P1 | S3-адаптер, крупные результаты вне PostgreSQL, проверенный retention | Доступ по принадлежности, целостность, воспроизведение и восстановление на реальном объёме |
| P1 | Нагрузочный профиль и метрики стенда | Не менее трёх размеров задач; измерены latency, память, очередь, MIP gap и деградация при отказах |
| Предметная верификация | История спроса, сетевые условия, цены и AC-схема | Независимый период/источник, проверенные тарифы и подключения; AC-режим отдельно при наличии схемы |

Без последней группы система выдаёт **проверенный сценарный расчёт**. Удаление демоподстановок и усиление безопасности не превращают предположенные входы в измеренные данные.
