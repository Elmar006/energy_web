## Типы документов и доказательств

- **Нормативный контракт:** `openapi.json`, миграции и код. Текстовые руководства объясняют использование, но при расхождении проверяется исполняемая версия контракта.
- **Операционные инструкции:** `START_HERE.md` и `RUNBOOK.md`. Закрытый production-профиль описан в `PRODUCTION.md` с незакрытыми блокерами; публичная многопользовательская готовность не заявляется.
- **Результаты эксперимента:** `docs/commission/*.json`, файлы протокола и lock — закреплённые артефакты. Их не изменяют после обновления модели; новый код получает новый протокол и результат.
- **Историческая проверка:** [журнал проверки 25 сентября](evidence/VERIFICATION_2026-09-25.md). Его тесты не заменяют проверки текущего commit.

## Правила сопровождения

1. При изменении публичного поля обновляются `openapi.json`, соответствующий пример и [handoff для фронтенда](frontend/BACKEND_HANDOFF.md) в том же изменении.
2. При изменении вычислительной логики обновляется [фактический статус](IMPLEMENTATION_STATUS.md), запускаются профильные тесты и создаётся **новый** экспериментальный протокол. Старый lock сохраняется.
3. Для каждого численного утверждения указываются вход, версия кода, метод сравнения и ограничения интерпретации. `assumed`, `derived` и `observed` не взаимозаменяемы; `observed` в пользовательском файле остаётся заявлением поставщика, пока первоисточник не проверен.
4. Разделяйте три вывода: технически задача выполнена, математический план допустим, качество обслуживания подтверждено в сценарной проверке. Ни один из них сам по себе не подтверждает целесообразность реального строительства.
